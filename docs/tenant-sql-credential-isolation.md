## Runtime Vault reader configuration

The API and AI Service register a read-only Vault AppRole reader using these configuration keys (for environment injection, use the normal double-underscore separator):

| Configuration key | Purpose |
|---|---|
| `Vault:Address` | Vault origin. HTTPS is required except explicitly enabled localhost development. |
| `Vault:Mount` | KV v2 mount name; defaults to `secret`. |
| `Vault:TenantSqlCredentialReader:RoleId` | Read-only AppRole role ID. |
| `Vault:TenantSqlCredentialReader:SecretId` | Read-only AppRole secret ID. |
| `Vault:AllowHttpForLocalDevelopment` | Must remain false outside localhost development. |

The role must read only the tenant SQL paths needed by the service. Keep the provisioning writer's role ID and secret ID separate and do not distribute them to API/AI Service containers. Configuration presence alone does not enable the service: startup validates the configured values, while production rollout still requires the authenticated request/worker flow, Studio lifecycle, least-privilege review and negative cross-tenant checks.

## Threat model

Protect tenant data against a compromised/misused app connection, an incorrect tenant-to-database mapping, and accidental access by a SQL principal intended for a different tenant. Signed `tenant_id` claims and deterministic database names remain necessary application routing checks, but do not stop a SQL principal that is authorized in every tenant DB. Tenant-specific SQL users also do not defend against a fully compromised provisioning administrator, SQL `sysadmin`, or host administrator able to retrieve all runtime secrets; those remain privileged trust boundaries and require audit, hardening and incident response.

## Recommended design

1. Keep the Platform catalog as non-secret metadata: tenant ID, database name, provisioning state, and a stable credential/principal reference plus credential version/status. Do not store plaintext passwords or encrypt them with a key stored beside the ciphertext in PlatformDB.
2. Select and name an authoritative secret owner before implementation. Preferred options are a managed secret service with workload identity and per-tenant secret paths, or a dedicated OS secret store with service-account ACLs and protected backup/key recovery. If a database-backed encrypted credential vault is chosen, its KEK must be held outside the database by a named KMS/HSM/OS key owner, with versioning, audit, rotation, revocation and disaster-recovery procedures. ASP.NET Data Protection by itself is not a cross-platform secret-management decision; its key ring would need durable, access-controlled storage and independent protection on both Linux and Windows.
3. Provision one least-privilege SQL login per tenant (or use an equivalent SQL-supported principal identity), create only its corresponding database user, and grant required object/role permissions in that database only. Avoid `db_owner`, `securityadmin`, server-wide grants, and implicit database access. Keep provisioning/admin credentials separate from API runtime credentials. Use SQL TLS certificate validation.
4. During provisioning, generate a unique high-entropy credential, create the SQL principal and target database permissions, write the secret to the approved store, validate the principal/database binding, then publish the catalog row as Ready. On any failure, keep routing closed and revoke/clean up partial state idempotently. Never log credentials or include them in job errors.
5. At request time, resolve the tenant from the authenticated claim, validate the Ready row and deterministic DB name, fetch the credential by the catalog's opaque reference, verify its tenant/database binding, and construct the connection string. Cache only briefly with bounded lifetime and explicit invalidation; do not put secrets in `HttpContext.Items` beyond the connection's current request lifetime if avoidable. A missing, stale, mismatched or unavailable secret must return unavailable, never fall back to a shared principal.
6. Define rotation/revocation, tenant deletion, restore, secret-store outage and key-loss behavior. Rotation should support overlapping old/new SQL credentials only for a bounded cutover window, then revoke the old principal. Restores must preserve or deliberately rotate credential references without copying another tenant's secret.

An alternative is one login per database with a shared password across tenants. This gives distinct SQL authorization identities but still means compromise of any one credential grants every tenant; it does not meet the intended credential isolation and is not recommended.

## Deployment surface

- **Compose / Release Deployer:** API and AI Service now receive endpoint/TLS-only `ConnectionStrings__Tenant` and `ConnectionStrings__AIStudio` templates; per-tenant SQL identities come from Vault at request/job scope. The old `aierp_data_runtime` login and its database grants may still exist, and `AIERP_DATA_RUNTIME_PASSWORD` remains in the local deployment `.env` even though these runtime templates no longer interpolate it. Inventory every consumer, remove the unused setting, and revoke or narrowly scope the SQL login only after compatibility and rollback review. Keep provisioning credentials separate from app-service credentials.
- **Linux/systemd:** `/etc/nexora/*.env` is root-owned and group-readable by the service group. That is reasonable protection for service-wide secrets, but does not provide per-tenant identity. Add a provider integration using the `nexora` service identity and durable key/secret recovery; do not place a master encryption key in the same env file as encrypted credentials.
- **IIS:** the installer injects settings into `web.config`; those files contain secrets and require strict ACLs. For tenant secrets, use a supported machine/service identity secret provider rather than expanding per-tenant plaintext into web.config. Recycle/pool identity and restore behavior must be included in rotation design.
- **AI Service and background workers:** they also open Studio or tenant databases. Request paths and retention workers use the tenant-aware provider; verify every non-request runtime consumer against the same tenant-specific identity and least-privilege policy. Retention/maintenance jobs must enumerate tenant identities and acquire the corresponding scoped credential, or use a separately approved narrowly scoped maintenance identity. No worker may retain the shared login as a fallback.

### ReleaseDeployer staging gap and acceptance

The generated ReleaseDeployer Compose is not yet aligned with the base Compose Vault path: it creates only the Platform database and shared runtime logins, injects `aierp_data_runtime` into API/AI Service connection strings, and has no Vault reader mounts or tenant-provisioning Worker. Do not treat generated staging deployments as tenant-SQL-isolated or production-equivalent until this gap is closed.

Implement staging provisioning as a distinct, disposable tenant lifecycle:

1. Allocate and persist a synthetic staging tenant identity for the deployment; never reuse the owning production tenant's SQL identity, secret path, database, or operational rows. Require the DBA-approved signed SQL provisioning boundary and a dedicated provisioning SQL principal before creating databases/logins.
2. Give the provisioning Worker a separate short-lived Vault writer AppRole scoped to the exact staging tenant's KV v2 ERP/AI Studio paths. Do not give the ReleaseDeployer, Platform API, or AI Service the writer role; do not use a root token, wildcard tenant writer, shared SQL password, or Platform runtime login for DDL.
3. Create/migrate that staging tenant's ERP and AI Studio databases, generate distinct high-entropy SQL credentials, publish both canonical component records, read them back, validate tenant/database/login binding, and prove each login can connect only to its own database (denied to the other component, another tenant and Platform DB). Mark the staging catalog Ready only after both components pass.
4. Generate API and AI Service Compose configuration with credential-free tenant/Studio endpoint templates, HTTPS Vault address, KV mount, read-only reader AppRole files and Vault CA mounted read-only. Mount reader files only into the runtime services (and the provisioning Worker when it must validate reads); never interpolate per-tenant passwords into `.env`, Compose, container environment, logs, or deployment results. Keep Platform DB credentials separate.
5. On failed creation, keep catalog state non-Ready and run idempotent cleanup: stop staging consumers, revoke only the staging SQL principals, remove only databases proven owned by that synthetic staging identity, and delete its Vault versions after consumers are gone. A retry must reconcile partial state safely. Preserve the staging databases and secret versions until rollback has restored the prior deployment; never revoke a credential still referenced by the rollback target.

Acceptance evidence before enabling generated staging deployments: (a) static Compose tests prove no shared tenant runtime login/password is present and reader/writer/CA mounts are service-scoped; (b) an isolated disposable SQL + Vault KV v2 test proves both-component create, migrate, write/read-back, own-database access and cross-database/Platform denial; (c) fault-injection tests at database creation, migration, Vault write/read-back, health check and rollback prove non-Ready fail-closed behavior and idempotent cleanup without touching another tenant; and (d) a ReleaseDeployer end-to-end run verifies both runtime services use the reader identity and successful authenticated ERP plus Studio operations. Do not use production data or production Vault paths for this acceptance. The current generated template has not passed these checks and must remain an explicit release gap until they do.

Then add ReleaseDeployer-level integration coverage proving the generated deployment provisions ERP and AI Studio for the synthetic tenant, writes/read-backs both credentials through the writer/reader roles, rejects cross-tenant and Platform DB access, and cleans partial failures without touching owner or production tenant state. ## Secret provider decision matrix

The provider protects and delivers SQL credentials; it does not create SQL isolation by itself. Every option below still requires a unique SQL login (or equivalent principal) per tenant, a matching database user, and reviewed grants only in that tenant's database. Provisioning/admin credentials stay separate from application identities. Platform API, AI Service and tenant-aware workers must all use the same approved provider contract.

| Option | Windows / IIS | Linux / systemd | Docker Compose | Key protection, backup and recovery | Rotation and tenant SQL effect |
|---|---|---|---|---|---|
| **Dedicated self-hosted Vault service** | Supported through a machine/service identity and TLS client authentication; IIS app-pool identity must be authorized to the needed paths. | Supported through a service identity and TLS client authentication. | Preferred for Compose when Vault runs as a separate trusted service or external host service; do not put a Vault root token in Compose. | Vault encrypts its storage, but operators must protect its seal mechanism and backup. Take and rehearse encrypted Raft/storage snapshots; separately escrow recovery/unseal material and protect any auto-unseal dependency. Loss of the auto-unseal key can make even backups unrecoverable. Restore and seal recovery are explicit operational responsibilities. | Central audit and versioned secret paths can support staged rotation. For each tenant, provision a new SQL credential, publish its new secret version, validate, switch consumers, then revoke the old login after the bounded overlap. Grants remain tenant-only and unchanged by the store choice. |
| **Native OS store / host-bound encryption** | DPAPI-protected local store or certificate-protected key material ACLed to a dedicated IIS app-pool identity. Keep the durable key ring/certificate separate from the app files. | `systemd` credentials encrypted to the host key and, where available, TPM2; expose only to the service unit. Service restarts and host replacement need a planned re-enrollment/recovery path. | Host-side store can supply a read-only mounted credential file to a service, but tenant-by-tenant runtime lookup/versioning needs an adapter and careful ACLs. Host-bound key material does not automatically follow a container to another node. | Strong local at-rest protection when ACLs and machine identity are sound, but a host loss/rebuild may strand secrets. Back up the encrypted payload plus independently protected recovery material/certificate; test restoring to a replacement host. DPAPI and TPM binding are not portable secret services. | Rotation requires provider-side update plus application cache invalidation/reload, with short overlap and old login revocation. Still one SQL login and own-DB-only grants per tenant; local store access may expose every tenant secret to an authorized app identity. |
| **Docker Compose secrets from host files** | Not applicable as a native IIS provider; files can be staged on Windows hosts, but that is a host-file design. | Compose grants a secret file to selected services as a read-only mount. Protect the source file with host ACLs and controlled provisioning. | Useful as a deployment bootstrap or for a small static set of service credentials. Compose file/environment-backed secrets do not provide a central per-tenant secret API or key lifecycle; use an external provider for dynamic per-tenant resolution. Docker Swarm secrets are a separate deployment mode. | Compose file-backed secret contents are sourced from host files; protect and back up those files out of band. Swarm stores secrets encrypted in its Raft log and requires manager/unlock-key recovery procedures. A database password copied into Compose/env or an image is not made safe by declaring it a secret. | File replacement/redeploy can rotate a mounted value, but existing app connections/caches must be drained or refreshed, and rollback must not revive a revoked login. A shared Compose credential does not isolate tenants; the app still needs individually scoped tenant logins and grants. |

**Recommendation:** For an installation that must support self-hosted Windows/IIS, Linux and Docker, use a dedicated self-hosted Vault service as the uniform authoritative provider, with per-tenant paths, workload identities, audited reads, tested encrypted backups and separately protected recovery/seal material. Keep Vault outside the application Compose stack's trust boundary where practical. Require Vault outage or identity failure to fail closed. For a single-host deployment with no staffed Vault operations, a host-native store can be a simpler approved deployment-specific choice, but only after replacement-host recovery and rotation are rehearsed; do not silently fall back to Compose env values. This recommendation assumes an operator can own Vault availability, updates, backup tests and recovery exercises.

The matrix reflects the documented platform behavior: [ASP.NET Core IIS Data Protection](https://learn.microsoft.com/aspnet/core/host-and-deploy/iis/data-protection), [systemd credentials](https://www.freedesktop.org/software/systemd/man/latest/systemd-creds.html), [Docker Compose secrets](https://docs.docker.com/reference/compose-file/secrets/), [Docker Swarm secrets](https://docs.docker.com/engine/swarm/secrets/), and [Vault seal and recovery](https://developer.hashicorp.com/vault/docs/concepts/seal). ASP.NET Data Protection key storage is not itself a per-tenant SQL secret provider.

### Open assumptions for the decision owner

- The supported footprint includes self-hosted Windows/IIS, Linux/systemd and Docker Compose, without assuming an external cloud KMS or managed secret service.
- Platform API, AI Service and relevant workers are trusted runtime consumers, but should authenticate as separate workloads and retrieve only what their role needs. A fully compromised app/host or provisioning administrator remains a privileged boundary.
- The SQL platform supports distinct SQL logins and database users for each tenant, and the DBA can issue grants and revoke old principals. Exact object-level permissions and non-API worker needs still require review.
- Vault is recommended only if an operator can run it as a durable service and maintain independent backup, seal/recovery custody and restore drills. Without that capability, choose a documented host-native implementation per deployment, accepting host-specific recovery limits.
- Credential rotation means staged SQL principal replacement with a bounded overlap; the application/provider will need explicit cache invalidation, outage behavior and secret version metadata before the guard can be removed.

## Decisions required before removing the guard

- Who owns the secret store and its authorization policy (Platform/DBA/operations), and what exact provider is supported on Linux, IIS and Compose?
- Is the design per-tenant SQL login/password, workload/managed identity, or another SQL authorization boundary? Who owns login creation and grants?
- Who owns encryption keys, their independent backup, rotation cadence, recovery and revocation?
- Which exact SQL objects/operations do API, AI Service, retention workers, migrations and reporting require? Replace broad reader/writer roles where practical with reviewed grants.
- How are existing shared-login grants inventoried and revoked after a two-tenant isolation acceptance proves the replacement?

### Existing Ready tenant credential cutover

The Tenant Provisioning Worker now has an explicit one-shot operation for existing isolated tenants. It finds ERP and per-tenant AI Studio databases whose catalog state is `Ready`, validates every canonical database name and database existence before writing, rotates each tenant SQL login password, writes it to that tenant's Vault KV v2 path, reads it back, and verifies own-database access plus denial to other tenant and Platform databases. It does not copy rows, run schema migrations, alter catalog state, or handle legacy shared databases. Non-Ready or non-canonical catalog state fails closed.

The command changes a SQL login password before publishing its Vault value, so stop Platform API, AI Service, Studio retention, and other tenant-aware consumers for the entire cutover window. The Worker needs the dedicated provisioning SQL connection and Vault writer AppRole; do not substitute the API Platform runtime account. Run from the deployment Compose project with the provisioning profile configured:

```powershell
docker compose --profile tenant-provisioning run --rm --no-deps tenant-provisioning-worker --migrate-existing-tenant-sql-credentials --confirm-api-ai-studio-stopped
```

The command prints only the number of verified ERP and AI Studio databases. A partial failure is safe to retry after fixing the cause while consumers remain stopped; it does not roll back a password already rotated in SQL and Vault. After a successful run, start API/AI Service, perform an authenticated tenant request and Studio database operation, then separately inventory and retire any legacy shared SQL login only after checking every consumer.
