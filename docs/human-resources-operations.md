# Operational HR period summary

Tenant administrators can open **İnsan Kaynakları → Dönem özeti** to review a period summary or download it as CSV. The API accepts `from` and `to` ISO dates at `/api/hr/period-summary` and `/api/hr/period-summary.csv`. Both endpoints require an authenticated `TenantAdmin` identity and data is restricted to that identity's tenant. Periods must be ordered and may span at most 366 calendar dates.

The summary contains employee headcount at the period end (employees hired by that date and not terminated before it), attendance record and distinct employee counts, worked and overtime minutes, plus leave requests whose date range overlaps the period. Leave request counts and requested days are grouped by request status. Requested leave days show each overlapping request's full requested total; they are not prorated to the selected period.

The summary and CSV omit employee names, personnel codes, user IDs, leave types, free-text notes, and row identifiers. Report generation and CSV export add tenant audit events `hr.period-summary.viewed` and `hr.period-summary.exported`, respectively, with the selected date range as the resource. Keep downloaded reports within the organization's approved access controls.

Employee records enforce tenant-level uniqueness for personnel codes and linked users. Attendance allows one record per employee and work date. Creating or approving a leave request is rejected when its dates overlap another pending or approved request for that employee; rejected and cancelled requests do not block it. Relational database writes serialize the creation overlap check with the insert. A concurrent duplicate or overlap returns HTTP `409 Conflict`, so the caller should refresh the list before retrying. Payroll rule drafts also return `409 Conflict` if another draft claims the same next version for the same effective date concurrently.

This is an operational aggregation of stored employee, leave, and attendance records. It does not calculate payroll, prepare SGK or tax declarations, or assert compliance with Turkish payroll or employment regulations. Payroll scope and any applicable legal requirements remain subject to product-owner and qualified domain review.

A termination date is the employee's last included employment date. The employee remains active through that date and is shown as terminated after it, using the API's UTC calendar date. Period headcount includes the employee when the selected end date equals the termination date. Leave days are entered by the requester and are not calculated from the date range or a work calendar; the entered amount cannot exceed the number of calendar days in the selected range. Overlapping-period summaries include the full requested amount for each request. Attendance is an optional daily record of entered worked and overtime minutes. A historical attendance record can be entered after termination if its work date falls within the employee's recorded employment dates. The system does not infer scheduled days, create missing attendance, or calculate payable time from these records.

Tenant administrators may save effective-dated Turkish payroll rule-set drafts with an HTTPS source URL. The shared structural rule-set contract is documented in [`payroll-rule-set-v1.schema.json`](schemas/payroll-rule-set-v1.schema.json); the API remains authoritative for semantic checks such as effective-range coverage, dimensional compatibility, and reference resolution. Version 1 parameter drafts use a shared JSON structure with per-parameter key, label, value type/value, unit, profile, effective dates, and source references. Sources can point to an official HTTPS publication or an employer-policy document/reference. Duplicate effective ranges for the same key and profile are rejected. A different tenant administrator must approve a complete rule set. Approval rejects overlap with an already approved rule set for the same tenant, jurisdiction, and tax year; relational databases run the overlap check and approval in a serializable transaction, returning `409 Conflict` when concurrent approvals deadlock. A parameter array may be empty when approved component formulas do not depend on scalar parameters; referenced parameters must match profile, type, unit, and effective period. Expression parameters are structurally checked against a bounded AST: constants, input/parameter references, arithmetic, min/max, comparisons, boolean conditions, `if`, explicit precision/mode rounding, and explicit unit conversions. Unknown operations, unit mismatches, or overlarge expressions are rejected. Approved rules must declare typed, unit-checked, profile/effective-dated input bindings for every formula input reference, with official and employer-policy sources; unresolved or uncovered references block approval. The runtime can bind compensation amount/target kind/currency/pay basis, period attendance minute totals, approved requested days for a named standard leave type, a prior-employer base amount by explicit employer base code and unit, and a candidate gross amount from an immutable employee snapshot. Missing attendance or a missing prior-employer base-code match is not treated as zero. Pending leave decisions and leave requests crossing a run boundary block binding because their period allocation is unknown. A net target is solved with a bounded search over `calculation.grossCandidate`; formulas that depend on this input must keep resulting net pay monotonic, and the runtime rejects sampled non-monotonicity or failure to converge within one kuruş. This only solves the net target using the employer's approved formulas; it does not supply tax law. Leave/pay-basis and partial-period conversion, same-employer year-to-date amounts can now be carried from contiguous second-user-approved prior formula periods when an explicit source binding requests a mapped base; statutory cumulative tax algorithms and finalized payroll results remain unavailable. The `POST /api/hr/payroll/runs/{id}/component-preview` endpoint returns formula-derived gross earnings, employee deductions, and net pay with line-level mappings. It does not persist/finalize a payroll result or generate a declaration file. Statutory validity is not checked. Payroll calculation and declarations remain disabled pending approved policy decisions, resolved inputs, and qualified legal/accounting review.

The leave request form and API use the canonical catalog keys `Annual`, `Health`, `Unpaid`, `Excuse`, and `Other`, with localized labels in the UI. New requests outside this catalog are rejected. These are catalog labels only: no leave type has an assumed pay effect. Each employer must map and approve the pay treatment before any future payroll calculation can consume leave records; missing mappings must block that calculation.

Rule-set schema v1 can also contain a `components` array for employer-defined payroll items. Each item has a unique key per profile/effective interval, a label, one structural category (`earning`, `deduction`, `employerCost`, or `exemption`), unit, profile, effective dates, and source references. There are no preseeded monetary items or statutory classifications; employers may add their own keys. Category does not imply tax, social-security, accounting, or net-pay treatment. Those mappings require separate authorized approval, and payroll calculation must stop when a required mapping is missing or unapproved. The component preview evaluates amounts, returns mappings, and aggregates only explicitly mapped income-tax and social-security bases; it does not post accounting entries.

Rule-set schema v1 also accepts a `payBases` array for employer-defined compensation bases. Each entry stores its code, label, unit, profile, effective dates, sources, and a constrained `periodMultiplier` expression. The multiplier converts the stored pay-basis amount into the run period amount: for example, a firm may define a multiplier from scheduled minutes, scheduled days, or calendar days, then apply its approved formula and unit. The selected pay-basis code must resolve to exactly one approved definition covering the profile and run period; the multiplier must evaluate to a non-negative value with the declared unit. Its required inputs and parameter references are checked with the same typed, dated rule bindings as component formulas. No monthly divisor, daily divisor, proration, or statutory conversion is seeded by the application; each employer must define and approve its own policy and sources. A missing, ambiguous, unapproved, negative, or dimensionally incompatible multiplier blocks calculation; net-target runs also require a positive periodized target.

2026 Türkiye özel sektör 4/a için araştırılmış resmi referans değerler [makinece okunabilir kaynak paketinde](payroll-turkey-4a-2026-official-reference.json) tutulur. Paket; ücret gelirine özgü GV dilimlerini (190.000/400.000/1.500.000/5.300.000 TL eşikleri ve %15/%20/%27/%35/%40 oranları), standart işçi/işveren SGK oranlarını, 2026 PEK alt/üst sınırlarını, asgari ücret ve damga vergisi bilgisini ve resmi URL'leri içerir. Bu, firma kural seti veya otomatik onay değildir: teşvik/istisnalar, kıst dönemler, her bordro kaleminin vergi/SGK matrahına girme kararı, kümülatif matrah/istisna algoritması, yuvarlama ve 1003A/1003B seçimi için firma profili ve ikinci yetkili onayı gerekir. Referans paketteki oranlar tek başına çalıştırılabilir bordro formülü olarak kullanılmamalıdır.

The restricted expression AST now has a bounded decimal evaluator for constants, typed input/parameter bindings, arithmetic, min/max, comparisons, conditions, explicit rounding, and explicit scalar-factor unit conversions. It checks runtime binding type and dimensional unit, and reports divide-by-zero/overflow as a failed evaluation. To approve a v1 rule set, it must contain at least one payroll component and every component must include a formula whose result unit matches the component unit. Each component also needs explicit, source-backed `incomeTaxBase`, `socialSecurityBase`, `accountingAccount`, and `declarationField` mappings covering the component effective period; the employer may use `EXCLUDED` as an explicit mapping decision. Drafts can still be saved before formulas and mappings are complete. The evaluator is wired into the component-preview route and runs against snapshot employee data. It can return formula-derived gross/net preview values, but does not persist an approved result; missing rule references still block evaluation. Tax, social security, accounting, and declaration mappings are not inferred from component categories.

`POST /api/hr/payroll/runs` creates an immutable internal draft snapshot for a selected employee group and either a calendar month or employer-defined period. It captures approved compensation history through period end, attendance, overlapping leave requests, approved previous-employer tax-base declarations, approved workplace calendars where required by a formula, and approved Turkish rule-set versions; the canonical JSON bytes are hashed with SHA-256. Snapshot reads require the compensation `view` permission, and run creation requires `change`. An employer-defined period remains internal and does not determine official declaration periods. Calendar-derived scheduled time is used only when an approved formula references it. Snapshot creation does not calculate, approve, or generate declaration files.

Previous-employer tax-base declarations are captured per employee and tax year through `/api/hr/payroll/compensation/prior-employer-tax-bases`. The submitter records either that no prior employer exists or supplies employer-defined base codes, labels, amounts, units, and a mandatory evidence/declaration reference. A different user with compensation approval permission must approve or reject the immutable version. Codes are deliberately not mapped to legal tax bases: an approved formula input must name the exact employer base code and matching unit; missing or ambiguous matches block preview, while an approved `NoPriorEmployer` declaration binds zero. No document is uploaded, verified, or retained by the reference field. Run snapshots include the declarations for the run tax year and block any employee without an approved declaration. Later approved versions are retained; consumers select the latest approved version for that employee and tax year. This capture satisfies the evidence-intake gate only; it does not calculate accumulated tax bases or clear the calculation-engine or declaration-profile/business-validation blockers.

Gross/net compensation targets are stored separately from personnel profile records. A change request records employee, target kind, positive amount, three-letter currency code, employer-defined pay-basis code, and effective date. Past effective dates are allowed, including dates before the request is entered. The request is immutable after creation; another user must approve it, and only approved rows are effective. The same employee cannot have two approved rows starting on the same date; the latest approved effective date applies until a later approved row. Once payroll runs exist, each approved run must retain its compensation snapshot when a later backdated change is approved; correcting a finalized run requires a separate, explicitly approved correction flow. Blocked run snapshots preserve approved compensation history; a finalized-run correction flow is not implemented yet. The API exposes a separate `erp.payroll-compensation` permission set: `view` for viewing, `change` for submitting changes, and `approve` for approval or rejection. No compensation permission is granted by the standard TenantUser baseline; tenant administrators can only access compensation through explicit allow rules for these permissions. Audit resources contain record IDs and versions, not amounts. Formula previews now convert targets using the approved pay-basis multiplier, and net-target solving compares against that periodized target. These remain internal formula outputs; they do not implement statutory gross-up or validate legal correctness.

The compensation endpoints are `GET /api/hr/payroll/compensation/capabilities` for the caller's permission flags, `GET /api/hr/payroll/compensation` for `view`-authorized salary records, `GET /api/hr/payroll/compensation/employees` for `view`-authorized employee choices, `POST /api/hr/payroll/compensation` for a `change`-authorized pending change, and `POST /api/hr/payroll/compensation/{id}/approve` or `/reject` for an `approve`-authorized second-user decision. Approve and reject share the `approve` permission. Both decisions preserve the immutable change request and actor/time audit fields. The capabilities route reveals only three booleans and uses the ordinary HR read permission. Salary amounts are returned only from the view-authorized records route. This API is tenant-scoped. Blocked run snapshot list/create/read endpoints exist; the component preview is not a final pay calculation. Run-level final approval/correction and official declarations are not implemented.

Payroll rule JSON rejects duplicate object-property names case-insensitively at draft creation and full rule validation. This prevents different parser paths from selecting different values for the same rule field.

A user with `change` but without `view` may still submit a compensation change by entering a known employee GUID. The employee-options endpoint and existing salary records remain restricted to `view`; the write action does not disclose salary values or employee directory choices.

Payroll draft list and snapshot detail reads require compensation `view`; list, snapshot, and component-preview access are written to the tenant audit log without salary amounts or formula results in audit resources.

Compensation amounts must be positive, have at most four fractional digits, and fit the database `decimal(18,4)` range (maximum `99,999,999,999,999.9999`). API validation and the form's numeric input enforce the same upper bound.

Run drafts block employees who start or terminate inside the selected period until an approved employer-specific partial-period proration rule is available. The component preview cannot imply a full-period amount for a partial employment period.

Approved leave requests crossing either run boundary are recorded as a run blocker because the current binder cannot allocate requested leave days into the selected period. The preview reports this before evaluating component formulas.

Attendance completeness now uses approved effective-dated workplace assignment and workplace calendar records, with a separately approved effective-dated employee calendar override. Calendar JSON contains all seven weekday expected-minute values (`0`–`1440`) and optional unique date overrides; no Turkish public-holiday calendar is seeded or inferred. When a formula uses attendance, exactly one workplace assignment and calendar must cover the period, any selected person override must cover the period, and every scheduled workday during employment must have an explicit attendance row (zero-minute rows are allowed). Missing/ambiguous configuration, assignment or calendar changes inside the run, invalid schedules, or missing workday rows block preview; missing days are never silently counted as zero. The immutable payroll snapshot includes the approved assignment/calendar versions used in the completeness check. Calendar/assignment drafts and approvals are tenant-admin-only, versioned by effective date, and require a different tenant administrator to approve. See `/api/hr/payroll/workplace-assignments`, `/api/hr/payroll/workplace-calendars`, and `/api/hr/payroll/employee-calendar-overrides`.

A `change`-authorized user can save a server-evaluated formula draft with `POST /api/hr/payroll/runs/{id}/calculate`. The result JSON and source snapshot hash are immutable and SHA-256 checked. `GET /api/hr/payroll/runs/{id}/calculations` lists tenant-scoped results; a different user with `approve` permission may approve or reject a pending formula draft. Approval records internal formula review only. It does not change the blocked run status, post payroll, attest to tax/social-security compliance, or enable official declarations. Missing employee/rule inputs still block draft calculation; declaration-profile/business-validation blockers may remain only because the saved output is explicitly marked formula-preview-only.

An approved result can be internally finalized by a third user with `approve` permission at `POST /api/hr/payroll/runs/{runId}/calculations/{calculationId}/finalize`; the creator and approver cannot finalize it. Finalization retains the immutable result and hash and records the finalizer and timestamp. It remains explicitly an internal result (`officialPayrollResult: false`), not a legal payroll accrual or official declaration. A correction is a new `POST /api/hr/payroll/runs` request with `correctionOfRunId` pointing to a finalized result for the same tenant, period and profile. The new snapshot captures the source run/calculation IDs and hashes; the original record is not overwritten. Download `GET /api/hr/payroll/runs/{runId}/calculations/{calculationId}/manual-package` returns a ZIP with CSV, source result JSON, package hash manifest and operator instructions. It is a manual review/entry aid only. It does not contain a GİB/SGK declaration payload; a firm-approved declaration profile, 1003A/1003B authority selection, field mappings and official schema validation remain required before such a payload can be produced.

For the initial ordinary private-sector 4/a baseline, the manual-package manifest records 1003A (`MUHSGK_21`, GİB V133.0) as the selected target format. This is a product default, not a statement of a tenant's actual filing authority or eligibility. The manifest lists employer, workplace, employee, wage-tax and SGK values still missing before an official XML can be generated. The 1003A/1003B choice remains subject to the tenant's real GİB authorization and approved declaration mapping.

The HR screen exposes the 1003A generator for finalized calculations. It provides a guided employer, withholding and employee form, plus JSON download/upload and an advanced JSON editor. Before enabling download, the client reconciles employee gross earnings against the finalized internal result, withholding gross against payroll gross, and withholding totals against employee income-tax withholding; it also checks required field shapes and numeric ranges. The API independently enforces that a different user with `approve` permission than the finalizer requests generation, snapshot and result hashes match, employee IDs and gross totals reconcile, and the run snapshot contains exactly one applicable approved rule set with a complete 1003A (`MUHSGK_21`) declaration profile and mappings. The XML must pass the checked-in GİB V133.0 XSD. This does not verify identity or registry authenticity, GİB code-list/business rules, tenant eligibility, statutory tax computation or government acceptance. Sensitive identity values are processed in the request and excluded from audit data; audit records include only the generated XML SHA-256.
The rule-set draft form also has an `Add a 1003A profile draft` helper. It adds a dated `1003A` / `MUHSGK_21` declaration entry for `TR-4A-PRIVATE` using the entered HTTPS source, period-rule reference, employer-policy reference, and employer tax-office/VKN/title/phone/branch values. The API requires the XML request employer values to match that second-approved profile exactly. This is only a draft. A tenant administrator must verify the real filing authority, complete all remaining rule-set inputs/mappings, and have a different authorized user approve the rule set before the API will accept 1003A XML generation.
For `incomeTaxBase` and `socialSecurityBase` mappings, rule-set v1 requires an explicit `baseTreatment` of `add`, `subtract`, or `exclude`, backed by the mapping source metadata and a second-user-approved rule set. `EXCLUDED` must pair with `exclude`; other target codes must use `add` or `subtract`. The preview reports per-employee aggregates grouped by mapping type and target code. Unit mismatches and decimal overflow fail the evaluation. These are employer-defined aggregation semantics: the application does not infer inclusion, statutory exemptions, ceilings, cumulative brackets, or legal treatment from a payroll item category or mapping code.
Rule-set inputs may use `sameEmployerYtdBase.amount` with an explicit `baseType` (`incomeTaxBase` or `socialSecurityBase`), `baseCode`, unit, effective period, and official/employer-policy sources. Run snapshots include only earlier same-year, same-profile formula results that a different user approved, with each result and source snapshot hash retained. The binder requires the employee's prior approved formula periods to cover continuously from January 1 (or the employee's hire date within that year) through the day before the current period. It sums exactly one matching code/type/unit contribution per prior period; a gap, overlap, missing mapping, mismatched unit, or hash failure blocks formula calculation. January 1 binds a known year-to-date opening value of zero. These prior values are approved internal formula previews, not finalized statutory payroll; the feature does not compute tax brackets, ceilings, exemptions, or report this as an official year-to-date balance.
Payroll confidentiality is gated independently from general HR employee access. Salary and prior-employer tax-base reads, payroll run/snapshot/formula-preview reads, formula-result approvals, and their writes require the corresponding compensation `view`, `change`, or `approve` permission; the capabilities endpoint exposes only those booleans. Denied requests do not create payroll audit events. This boundary is covered by `Payroll_sensitive_reads_and_writes_require_explicit_compensation_permissions`; it does not enable official payroll calculation or relax existing blockers.
