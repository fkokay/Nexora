# E-document tenant configuration: design gaps

**Status:** tenant-admin configuration remains blocked on security and platform ownership decisions. IntegrationHost now fails closed for `tr.e-document.submit`, even when a host-wide generic adapter is configured. No credentials, vendor documents, vendor sandbox, database, or outbound provider calls were used.

## Current code evidence

- `tr.e-document.submit` runs through the generic JSON-over-HTTPS adapter in `src/Extensions/AIERP.IntegrationHost/IntegrationExecutionEndpoint.cs`. The host reads the provider URL, path, `AllowedHosts`, and request/response mappings from IntegrationHost configuration. E-document request and response mappings are required; missing mappings make the adapter unhealthy and stop delivery.
- Tenant credentials are resolved by `src/Extensions/AIERP.IntegrationHost/FileIntegrationSecretResolver.cs` from a tenant-specific directory under `IntegrationSecrets:RootPath`. The service mount is read-only. The resolver checks path containment and rejects reparse points, but this does not establish encryption at rest or provide an API write path.
- `src/Platform/AIERP.Platform.Infrastructure/IntegrationOperationCipher.cs` uses AES-GCM with tenant, operation, and purpose associated data for queued request/result bodies. Its key is `IntegrationQueue:EncryptionKey`; architecture documentation says it must remain stable and be backed up securely. Its allowed purposes are `request` and `result`, and the helper is scoped to integration operation data.
- `src/Platform/AIERP.Platform.Infrastructure/ApiKeyCipher.cs` and `TenantAIProviderSettings` show a saved AI provider key pattern. New AI key ciphertext uses AES-GCM with tenant and provider-purpose associated data (`openai-api-key` or `nvidia-api-key`), using `AI:SettingsEncryptionKey`. The helper remains scoped to AI provider keys and does not define e-document credential ownership, ingress, rotation, or handoff. Existing unversioned and tenant-only `v2` ciphertext remains readable until a compare-and-swap migration is run; no automatic database re-encryption has occurred.
- `src/Hosts/AIERP.Api/IntegrationExecutionApiEndpoints.cs` exposes tenant-scoped e-document submission and operation management, but no tenant provider/mapping settings or credential write endpoint was found. The API and IntegrationHost do not currently share a documented secret ingress or resolver contract.
- IntegrationHost validates HTTPS and requires the exact host to appear in the configured `AllowedHosts` for that adapter. This is host-owned configuration, not tenant-admin input. No central e-document allowlist owner, source, or change process is documented.

## Decisions needed before implementation

1. **Credential storage and handoff owner:** Choose which service owns the durable credential and how the IntegrationHost obtains it. Define the authenticated write-only ingress or encrypted handoff, tenant identity binding, secret reference lifecycle, rotation/revocation behavior, and how plaintext is kept out of logs, audit resources, responses, and persistent queues. The existing read-only secret mount cannot accept tenant-admin writes.
2. **Protector and key lifecycle:** Security must approve the protector and its key source for these long-lived credentials. Specify which runtime holds the key, how API and IntegrationHost deployments access it, rotation and rollback behavior, backup/restore handling, and tenant/integration/credential-version binding. The queue cipher is a reusable cryptographic implementation pattern, but its current key purpose and data lifecycle are for queued operations; extending it to credentials needs explicit owner approval. Do not add a new cipher or repurpose the AI provider key helper without that decision.
3. **Centrally controlled hostname allowlist:** Name the owner and authoritative configuration source for e-document hosts. Define how a tenant's HTTPS endpoint is checked against that central list, and who can approve additions. Tenant admins must not be able to broaden the central list. Define whether host entries include sandbox and production separately and how host changes are reviewed and audited.
4. **Configuration ownership and contract:** Decide whether provider selection, base URL/path, request mappings, response mappings, and credential reference live in tenant-scoped Platform data or IntegrationHost configuration. Specify versioning and how the worker/host receives a consistent config snapshot. Keep mapping validation fail-closed and do not issue an outbound validation call when saving settings.
5. **Audit contract:** Specify safe event names and fields for config changes, credential replacement, and mapping changes. Audit metadata must identify actor, tenant, and changed setting categories without storing secret values, ciphertext, provider payloads, or sensitive response bodies.

## Implementation gate

The ownership decisions are still open, so no tenant configuration API, data model, migration, secret persistence, or host-allowlist management was introduced. The existing IntegrationHost file resolver is read-only and host-mounted; its tenant-id lookup is suitable only for resolving existing mounted per-tenant files, not as tenant-admin secret ingress. The AI provider cipher now binds new AI keys to tenant and provider purpose, but remains specific to AI provider settings; the integration queue cipher has a different data lifecycle and purpose. Neither establishes an approved e-document credential contract. Existing AI ciphertext is not automatically rewritten: legacy values remain in their stored format until an explicit compare-and-swap migration processes them.

Fail-closed behavior is now explicit: IntegrationHost reports the reserved e-document adapter invalid and rejects execution before resolving a credential or making an outbound request, even if host-wide endpoint and mapping values exist. The focused contract tests assert this behavior and preserve the existing requirement that e-document request/response mappings are explicit. No vendor call or secret access is needed to run those tests. This does not implement the tenant-admin feature; the decisions above remain prerequisites.

After the owners decide the items above, implement tenant-admin-only read/write settings with tenant isolation, write-only secret ingress and masked presence responses; validate provider and explicit request/response mappings; enforce the centrally owned HTTPS hostname allowlist; and emit redacted audit events. Add focused tests for tenant isolation, ciphertext at rest, role denial, rejected hosts, invalid/missing mappings, and absence of secret values in API responses and logs. Saving settings must not contact the provider. If a schema change is needed, prepare only the migration source and static release candidate; do not apply it as part of this work.

The adapter contract test source covers the provider-independent request/response mapping seam, but its execution is still pending the shared test-runner slot. It does not resolve the ownership and key lifecycle decisions listed above.
