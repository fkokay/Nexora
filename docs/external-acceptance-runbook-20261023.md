# External acceptance runbook (2026-10-23)

This runbook covers seven acceptance activities that need an external account, an authorized human review, or customer-equivalent staging. The local fixtures and test reports listed here are preparation evidence only. Do not record credentials, tokens, private keys, customer data, payment data, raw AI answers, exploit payloads, or document bodies in repository evidence.

## Status and execution boundary

Local preparation is available for each activity; none of the external acceptance gates below is marked complete by this runbook. GitHub was queried read-only for repository, pull request, workflow, and code-scanning status. No live provider or GitHub write was called, no user/customer data was sent, no staging target was probed, and no HA/deployment/database operation was run. The current working tree already contains unrelated edits; this document is additive and does not attest that those edits are a reviewed release.

For each activity, create the evidence record in the approved restricted release/evidence store, then add only a redacted summary or artifact identifier to the release record. Use the following common metadata: run ID, UTC start/end, approved build/commit and image/package digests, environment identifier, operator and reviewer pseudonyms, outcome, evidence links, deviations, and owner sign-off.

## 1. Authenticated GitHub App end-to-end test

**Local preparation:** Unit coverage exists for installation-token claims, PR create/reuse and ready-for-review behavior. TestServer coverage exists for signed webhook transitions, stale events and invalid signatures. These tests use fakes and do not establish real installation permissions or callback reachability. See `tests/UnitTests/AIERP.Platform.UnitTests/GitHubAppInstallationTokenProviderTests.cs`, `GitHubPullRequestPublisherTests.cs`, `GitHubPullRequestLifecycleTests.cs`, `GitHubWebhookSecurityTests.cs`, and `tests/IntegrationTests/GitHubPullRequestWebhookIntegrationTests.cs`.

**Required access and inputs:** GitHub organization/repository owner; disposable repository and candidate branch; authorized test operator; GitHub App installed only for that repository; App ID and slug; private key PEM and webhook secret held in the approved secret store; production HTTPS base URL and reachable callback `https://<host>/studio/github/setup-callback`; Studio redirect URL; webhook endpoint `https://<host>/studio/github/webhook`; `pull_request` webhook subscription; approved candidate commit; and an owner-authorized test window. Configure the matching process settings documented in `.env.example`: `GITHUB_APP_ID`, `GITHUB_APP_SLUG`, `GITHUB_APP_PRIVATE_KEY_PEM`, `GITHUB_APP_WEBHOOK_SECRET`, `GITHUB_APP_SETUP_CALLBACK_URL`, and `GITHUB_STUDIO_REDIRECT_URL`. For checkout, installation Contents permission must be read-only. For the separately authorized PR publication/review/comment operations, grant only the required Contents and Pull requests write permissions; the code requests a repository-scoped token with Contents read for checkout or Contents write plus Pull requests write for write operations. Metadata read is the platform baseline. The App installation, permissions, callback reachability, and webhook delivery are not confirmed by the current read-only check; the repository installation API requires GitHub App authentication, which is not available through the current CLI user session. Do not broaden the installation to unrelated repositories. Keep publication disabled until the repository owner authorizes the test write. Never put secret values in this runbook or evidence.

**Run and evidence:** Complete Studio authorization for a test project; confirm project-to-installation association; prove checkout uses a read-scoped token; publish one reviewed disposable candidate only after write authorization; verify PR create/reuse and ready-for-review behavior; deliver signed open, synchronize, closed and merged events; verify comment/review synchronization and invalid-signature rejection. Store `github-app-e2e-<run-id>.json` with pseudonymous installation/repository IDs, commit, permission outcomes, PR reference if authorized, webhook event IDs, timestamps and redacted logs. Never include key material or installation tokens.

**Pass criteria:** Only the disposable repository is accessible; checkout succeeds with read-only Contents scope; explicitly authorized publication creates or reuses the expected PR with no duplicate; each valid webhook transition is reflected once and in order; invalid signatures are rejected without state change; unauthorized repository access and write operations fail; all evidence is redacted and the repository owner signs the result. Any missing event, excess scope, duplicate write or unexplained state transition fails the gate.

## 3. AI answer quality with human review

**Local preparation:** `tests/UnitTests/AIERP.Platform.UnitTests/EvaluationSets/erp-assistant-live-quality-v1.json` contains five synthetic cases. `tests/integration/Invoke-LiveErpAssistantHumanReview.ps1` enforces one Responses API request, no retry, no tools, `store=false`, no tenant data, two independent reviewers and third-reviewer adjudication for disagreements. Existing prior live attempts returned HTTP 429 with no scoreable answers; that is not a pass.

**Required access and inputs:** OpenAI account owner supplies an approved model and securely provisions process-scoped `AIERP_LIVE_EVAL_PROVIDER=OpenAI`, `AIERP_LIVE_EVAL_OPENAI_MODEL`, and `AIERP_LIVE_EVAL_OPENAI_API_KEY`. Obtain approval to send the fixed synthetic prompts in the evaluation set. Provide two distinct independent reviewers and, if any scores disagree, a third distinct adjudicator. Do not use production data or paste raw answers into logs/evidence.

**Run and evidence:** Run the script interactively once in an approved environment. Reviewers score independently and must not inspect each other's scores. Retain `tests/UnitTests/AIERP.Platform.UnitTests/TestResults/ai-evaluation/live-human-review-report.json` or a restricted evidence copy. The report stores set/model metadata and scores but not raw answers.

**Pass criteria:** Exactly five case answers are returned from one request; request count is one, retries zero, tools disabled, `store=false`, and tenant data unused; each case's critical checks pass; each applicable rubric dimension scores 2 after required adjudication; both reviewers approve and, when needed, the adjudicator approves; report `decision.accepted` is `true`. HTTP 429, missing/duplicate answer, any score below 2, failed critical check or absent approval is not accepted. Resolve quota/rate limits before seeking authorization for a new one-request run.

## 4. E-document and payment provider sandboxes

Treat e-document submission and payment flows as separate provider acceptance tracks; a pass for one does not accept the other.

**Local preparation:** E-document draft, independent approval and tenant-isolation coverage exists in `tests/IntegrationTests/IntegrationQueueIntegrationTests.cs`; the integration contract supports a provider-neutral request and response mapping. `src/Extensions/AIERP.IntegrationHost/README.md` documents tenant-scoped secrets, HTTPS host allowlists, stable idempotency and indeterminate-operation reconciliation. No e-document provider adapter is configured by default. Existing SDK tests do not contact a provider.

**Required access and inputs:** Provider and business owners; separate e-document and payment sandbox accounts/tenants, endpoints and allowlisted hosts; tenant-scoped sandbox credentials in the approved secret store; provider API/schema versions and approved request/response mappings; provider test accounts/certificates as applicable; synthetic documents and payment instruments; two distinct tenant administrators for document approval; provider-portal reconciliation access; agreed test limits and owner sign-off. Confirm these are sandbox credentials/endpoints before enabling an adapter.

**Run and evidence:** For e-documents, preview and prepare a synthetic draft, prove creator cannot approve, approve with a second admin, deliver through the queue, and verify accepted, rejected, timeout/indeterminate and reconciliation behavior with a stable idempotency key. Verify tenant isolation and that no live endpoint is configured. For payments, use vendor-approved test-mode instruments to exercise the agreed authorize/capture/refund or order flow, idempotent retry, decline, timeout and reconciliation cases; keep any PayPal approval/capture action within the explicitly approved sandbox scope. Create separate `e-document-sandbox-<run-id>.json` and `payment-sandbox-<run-id>.json` records with mapping versions, synthetic case IDs, operation/request IDs, status transitions, idempotency/reconciliation outcomes and redacted logs. Do not retain payloads, personal/tax details, credentials or card data.

**Pass criteria:** All expected accepted/rejected mappings match provider results; draft approval requires an independent administrator; cross-tenant reads/actions are denied; retries preserve the same idempotency key and produce no duplicate external operation; indeterminate outcomes are reconciled in the provider portal before retry; failure and timeout paths are bounded and visible; only sandbox hosts/accounts are used; provider and business owners sign off. Any live endpoint, duplicate effect, unexplained result or missing reconciliation evidence fails the relevant track.

## 5. Authorized penetration test

**Local preparation:** `tests/security/README.md` distinguishes local smoke/static/dependency checks from a penetration test. Those local checks do not authorize or establish a security assessment of a deployed target.

**Required access and inputs:** Written authorization from the security owner; named qualified tester; exact customer-equivalent staging URLs/IPs and build identity; explicit API, Studio, Marketplace and integration scope; test identities for tenant/admin/maintainer roles with synthetic fixtures; permitted techniques and prohibited actions; time window, rate limits, emergency contact, data-handling rules, and finding/remediation owners. No production target or third-party system may be included implicitly.

**Run and evidence:** Test the approved scope for tenant isolation, authorization/role escalation, SSRF and redirect controls, package/signature handling, input/path boundaries and secret exposure. Stop and contact the emergency owner on instability or scope ambiguity. Store the signed detailed report in the restricted security evidence system; commit only `penetration-test-<run-id>-summary.md` containing build/scope, dates, finding IDs/severity, remediation owner/status and redacted disposition. Do not place exploit payloads or secrets in the repository.

**Pass criteria:** The tester confirms the tested build and exact scope; no unresolved Critical/High finding remains unless the security owner records a formally accepted exception with owner and due date; each lower-severity finding has a disposition and owner; retests verify fixes; no test escaped scope or caused unapproved data change; the security owner signs the final report. A local security smoke, SAST or dependency scan cannot satisfy this gate.

## 6. Representative-data load test

**Local preparation:** `tests/performance/Invoke-SeededReadPathLoadTest.ps1` performs an authenticated read-only scenario for dashboard, stock items and CRM opportunities. Its synthetic acceptance fixture validates preflight and report redaction without calling a live ERP API. `tests/performance/README.md` documents both limits. The fixture is not API capacity evidence.

**Required access and inputs:** Operations/API owner; dedicated non-production API and isolated SQL; seeded non-customer tenant with at least 100 stock items and 100 CRM opportunities (or an explicitly approved changed floor); process-scoped test credentials; monitoring/DB metrics access; approved request count, concurrency, p95/error thresholds, duration, test window and stop limits. Do not use customer data.

**Run and evidence:** Verify the target URL and tenant before execution. Set `AIERP_LOADTEST_EMAIL` and `AIERP_LOADTEST_PASSWORD` in the process environment and run `Invoke-SeededReadPathLoadTest.ps1` with the approved tenant/profile. Default profile is 300 requests per endpoint, concurrency 25, p95 at most 1,000 ms and errors at most 1%; these defaults are development baselines, not an SLA. Capture host/SQL CPU, memory, connection pool, query saturation, errors and latency alongside the generated `performance-seeded-read-baseline.json`. The report excludes credentials, identifiers and response bodies.

**Pass criteria:** Dataset count gates pass before requests; only the three approved authenticated GET paths are measured; requested traffic completes; p95 and error rate meet the explicitly approved limits; no unexpected writes, cross-tenant access, data exposure or saturation stop condition occurs; metrics cover the complete run and the operations owner signs off. A missing seeded-data gate, unauthorized endpoint, limit breach or incomplete monitoring is a failure/inconclusive result, not a pass.

## 7. High availability and failover exercise

**Local preparation:** `docs/production-ha-acceptance-runbook.md` defines the multi-node procedure and evidence checklist. Local release-failure fixtures validate recovery rules only; they do not demonstrate multi-node behavior. The current deployment profile is single-host, so HA acceptance requires an intended multi-node architecture and customer-equivalent staging.

**Required access and inputs:** Operations owner and DBA; at least two staging application/deployer nodes; shared lease/coordination backend and fencing mechanism; staging load balancer/traffic manager; SQL primary/secondary failover topology; monitoring and on-call alert route; synthetic workload/data; approved RTO/RPO, maintenance window, rollback procedure and emergency stop authority.

**Run and evidence:** Follow Gate 5 in `docs/production-ha-acceptance-runbook.md`: test concurrent promotion exclusion; isolate the lease owner and prove stale-token rejection after takeover; drain/remove one API node; perform planned SQL failover; verify reconnect, consistency and alerts; restore node/SQL roles and reconcile release and lock state. Record time-stamped before/during/after health, traffic, errors, lock/fencing state, SQL role changes and alert delivery in `production-ha-acceptance-<run-id>.json`; include measured recovery durations and redacted logs.

**Pass criteria:** Concurrent promotion is excluded; takeover is safe and a former owner cannot publish with a stale fence; remaining application nodes serve traffic within the approved interruption/error limits; SQL failover restores service and consistent data within agreed RTO/RPO; alerts reach the on-call route; restoration leaves nodes, roles and locks reconciled; operations and DBA sign the evidence. A one-node check, package validation or database restore drill alone is not HA acceptance.
