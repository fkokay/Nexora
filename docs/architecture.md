# AI ERP Platform: Architecture and Scope

## Architecture decision

Nexora ERP and AI Development Studio run as separate products with separate service boundaries. The ERP Platform API owns authentication, tenant membership, tenant selection, ERP workflows, and platform audit events. AI Development Service owns Studio project metadata, access grants, development requests, approvals, AI-assisted planning and code suggestions, and coordination with the Workspace Runner. The Workspace Runner owns source checkout and tightly scoped filesystem operations. It has no database dependency or Docker socket. A separate `workspace-sandbox` runs explicitly approved test jobs; it does not share the workspace checkout or network with test code.

The current tenant model uses a shared SQL Server `AIERPPlatform` database with `TenantId`-scoped records and queries. Separate PlatformDB/TenantDB/AIStudioDB databases and per-tenant database routing are future work. The ERP domain is a modular monolith; the AI Development Service and Workspace Runner are separately deployable ASP.NET Core hosts.

## Services and clients

- `AIERP.Api` provides login, tenant selection, ERP endpoints, bootstrap setup, and health checks.
- `AIERP.AIService` provides the tenant-scoped Studio API and calls Workspace Runner using short-lived signed service tokens scoped to one workspace or project and one operation.
- `AIERP.WorkspaceRunner` provisions and inspects checkouts, applies approved single-file changes, and prepares bounded test snapshots. It is not published to the host and has no database or Docker socket.
- `AIERP.WorkspaceSandbox` reads jobs from a private shared queue volume. It has no workspace volume, database, signing key, Docker socket, or network connection.
- `frontend/erp-web` is the authenticated ERP client. `frontend/development-studio` is a separate Vite client served by Nginx on port 5174. Studio authenticates against Platform API and enforces tenant/project permissions through AI Service.

## AI Development Studio

Projects are tenant-scoped and register a display name, HTTPS repository URL, and default branch. Tenant administrators register projects; maintainers grant or revoke Viewer, Contributor, and Maintainer access for active members of the same tenant. The last Maintainer cannot be removed. Development requests can be attached to a project and workspace request; approval or rejection is limited to tenant administrators and project Maintainers. A requester cannot approve their own workspace request.

After approval, an authorized Maintainer or TenantAdmin can create a shallow checkout on the configured public HTTPS Git host allowlist (GitHub by default). Repository URLs cannot contain credentials, Git redirects and hooks are disabled, and private or loopback destinations are rejected. The Runner creates a deterministic local `aierp/workspace-<workspace-id>` branch and records the checkout commit. Changes remain in that workspace branch; Studio does not push them or create a pull request.

Project Explorer lists directory metadata and previews UTF-8 text files up to 128 KiB. Its bounded project map uses file names and extensions without reading source contents. Branch status and diffs are separate, explicit read operations. Search results are not automatically sent to AI. A user can select at most five search excerpts for one-time AI analysis after consent; Studio re-reads the exact lines from the authorized checkout and verifies they still match. One explicitly selected Git diff can also be sent for ephemeral review after separate consent. These requests use `store=false`, retain no prompt or source text, and audit only workspace identifiers and operation outcomes.

AI Architect receives a confirmed request and bounded project metadata, not source files. It returns a schema-validated plan that an authorized user may explicitly save. AI Tester can draft manual scenarios from a confirmed request and test-target metadata after AI-sharing consent; these scenarios do not execute. Studio chat sends only the conversation text that the user chose to submit and project/branch names, with no automatic source attachments or tools. Chat messages are retained in the Platform database; users can delete conversations after confirmation.

AI Developer can propose a replacement for one explicitly selected source file (up to 32 KiB) or propose one new file. Sharing existing source requires separate consent. The user reviews a diff and separately approves applying it. Runner checks the original SHA-256, rejects unsafe paths and symlinks, writes atomically, and refuses to overwrite a new-file target. An approved rollback restores prior bytes only while the file still matches the applied hash. Changes, sharing, approval, application, and rollback are audited. AI Developer also supports coordinated proposals for 2–5 explicitly selected source files, with a 64 KiB aggregate input limit. Source-sharing consent is required; every proposed file is reviewed and applied separately through the existing SHA-256 stale-source check, audit, and approval path. No file is automatically applied.

Maintainers and TenantAdmins can explicitly create a local commit from the isolated workspace branch. The API requires the current HEAD and selected Studio change IDs; Runner revalidates the full changed-path set, saved change records, and current file hashes. It builds the Git tree/index without invoking hooks or content filters and updates only the isolated local branch. The commit is audited and can then be tested against its clean HEAD; the operation never pushes to the remote repository.

## Test Center and execution sandbox

Test Center discovers likely .NET, Node.js, Python, Go, and Rust targets from bounded manifests and file names. Only discovered `.csproj` projects, `package.json` files with supported native Node test files, Python test files, Go `_test.go` files inside a Go module, and Cargo manifests with Rust test files can currently run, and only after a Maintainer or TenantAdmin confirms execution. The Runner revalidates the selected target, then creates a source-only archive (up to 20,000 files, 100 MiB total, 16 MiB per file). It skips Git metadata, hidden/generated/dependency folders, symlinks, and secret-named paths. The job records the checkout commit, archive SHA-256, and dirty-worktree flag.

The separate sandbox runs fixed commands as UID 65532 with a cleared environment. Maintainers and TenantAdmins can separately build discovered .NET projects using `dotnet build --no-restore` after an offline restore; builds use the same bounded source snapshot and do not modify the checkout. .NET restore uses only NuGet packages baked into the image; unavailable packages are reported without network access. Node.js uses the built-in `node --test` runner only. `npm` scripts are never invoked, `node_modules` is excluded, and projects declaring package dependencies are reported unavailable. Python runs the image-provided pytest with no project packages installed; missing imports are reported unavailable. Go runs fixed `go test -mod=readonly .` commands with network and toolchain downloads disabled; modules declaring `require`, `replace`, or `toolchain` directives are reported unavailable. Rust runs fixed `cargo test --offline` commands only for standalone packages without dependency tables or workspace manifests; crate dependencies are unavailable offline.

The sandbox has no network, Docker socket, database, signing key, or workspace volume. The container uses a read-only root filesystem, drops capabilities except those required by its supervisor, enables no-new-privileges, and is limited to 2 CPUs, 2 GiB memory, and 256 PIDs. Each command has a 90-second total restore/test limit and output is capped. The per-job source snapshot lives on a bounded 2 GiB tmpfs; executable permission is enabled only on that job-temp mount so compiled Go/Rust test binaries can run, while the container root stays read-only. Compiler temporary files stay inside the job directory, which is deleted after execution. The shared queue accepts at most eight outstanding jobs; jobs waiting over 20 minutes or running over 10 minutes expire. Results are retained for up to seven days. Studio checks release readiness by comparing current Git status with successful sandbox evidence for the same clean HEAD. A Maintainer or TenantAdmin can save a release candidate after the API revalidates both facts against Workspace Runner; the append-only record stores the branch, HEAD, test job, target, and snapshot hash and creates an audit event. Candidate records do not create packages or deploy. A TenantAdmin other than the candidate creator can append one approval or rejection with a required note; the API rechecks the candidate commit and sandbox evidence before recording the decision. Decisions cannot be overwritten; a new candidate is needed for another review. A Maintainer or TenantAdmin may assign one immutable SemVer 2 version number to an independently approved candidate after revalidating its clean HEAD and test snapshot. Version strings are unique per project; assignment records the exact commit and audit event and does not create a package or deploy. After approval, a Maintainer or TenantAdmin may request an AI-generated pull request title and description. The API revalidates the clean candidate HEAD and successful test snapshot, and sends only the user-provided summary plus bounded project/branch/commit/test metadata to OpenAI with storage disabled; source files and test output are excluded. The result is an editable draft. Publishing requires a second explicit confirmation and an independent candidate approval. The AI Service requests a short-lived GitHub App installation token scoped to the single repository; the Runner pushes only the exact clean candidate commit, refuses to overwrite a different remote branch, and does not persist the token. The API creates or reuses a draft pull request and audits the result. Configure `GITHUB_APP_ID` and `GITHUB_APP_PRIVATE_KEY_PEM` in the deployment secret store; each publishing action supplies the repository installation ID. A Maintainer or TenantAdmin can create one deterministic ZIP for an assigned version after an independent approval and a fresh clean-HEAD/test-evidence check. The Runner excludes hidden/secret paths, symlinks, dependency and generated directories, and enforces file-count and size limits. `AIERP-RELEASE.json` records the commit, version, test snapshot, and each included file hash; package SHA-256 and size are persisted. Authenticated downloads are rechecked against that hash and audited. The local Release Deployer is a separate, internal service. Only the AI Service can call it with a two-minute JWT bound to one tenant, project, deployment, and operation. It reads packages from the Runner’s read-only package volume, verifies the archive SHA-256, manifest, every file hash, size, and path, then creates trusted Compose/Dockerfile definitions; package contents cannot supply deployment configuration. Staging runs as a project-scoped Compose stack with its own SQL Server and persistent data volumes, on an internal Docker network. Only the Studio port is published, bound to host loopback (`localhost`); the staging database and service ports are not published. Each staging service has CPU, memory, and PID limits, and the local host allows at most two active project staging stacks by default. API/AI/Runner containers run as the non-root app user with read-only root filesystems; ephemeral Data Protection and temporary files use bounded tmpfs mounts. Bootstrap credentials and deployer state are encrypted at rest, and the bootstrap password is returned once to the initiating user. A staging deploy, redeploy, rollback, and destroy each require a separate explicit user action and are audited.

The Deployer requires the Docker Engine socket, which gives it host-wide container-management power. It is isolated from public ingress, has a read-only package mount, a private service network, a read-only root filesystem, dropped capabilities, and short-lived scope-bound callers. Since Docker socket access itself is not confined by those container controls, this local Compose integration is intended for a trusted development machine. Rollback restarts older application code against the same environment database; it does not reverse schema migrations. Staging and local production Compose stacks use a separate one-shot migrator service, while the API starts with automatic migrations disabled. Production updates require separate user confirmation for deployment and schema migrations; before an update, the Deployer writes a SQL Server backup into the separate persistent `aierp-production-backups` Docker volume and verifies that the file is visible through its own read-write mount before proceeding. The SQL data and backup volumes are distinct but both remain on this host. After a failed release, the Deployer attempts to restart the previous application stack and health-checks it when Compose starts successfully; the result is written only to Deployer logs. A TenantAdmin can request an audited restore of the current release's pre-deployment database backup together with its recorded previous application package. The Deployer verifies that backup, creates a verified safety backup of the current database, stops the API, restores the selected database, starts the matching application, and health-checks it. If the target application fails, it attempts to restore the safety backup and restart the current application; that recovery result is written to Deployer logs.

After a successful staging deployment, a Maintainer can submit a reasoned production-promotion approval request. Only a different TenantAdmin may approve or reject it, and the decision and notes are audited and immutable. Approval alone does not start deployment. A different TenantAdmin must separately confirm the local production deployment and, in a second confirmation, authorize schema migrations. The selected production target is this machine’s Docker Compose. Production is bound to localhost on a separate port, uses a persistent SQL data volume and the separate `aierp-production-backups` volume, and the Deployer attempts to restart the prior application package when an update fails, then health-checks it if Compose starts successfully. The first bootstrap password is shown to the initiating administrator once. This is a single-host local deployment, not an internet-facing high-availability environment; Production history exposes a destructive restore for the active release or a failed release when its previous app package and pre-deployment backup are recorded; a typed backup-deployment-ID confirmation is required.

Contributors can request AI analysis for a failed or incomplete sandbox test/build after explicit confirmation. The AIService re-reads the job from Workspace Runner, masks common API keys, bearer tokens, credential assignments, and URL credentials, and sends at most 16,000 characters of log output with bounded job metadata to the configured provider. The AI returns a structured likely cause, human-reviewed next steps, and limitations; it cannot execute commands or apply fixes. Raw job output and analysis are not persisted by this endpoint; only request/completion audit metadata is stored.

## ERP modules

### Cari

Cari provides tenant-scoped customer and supplier account cards, search, pagination, detail, create/update, and activate/deactivate. Codes are uppercase and unique per tenant. SQL Server rowversion protects concurrent updates. Accounts support tenant-owned groups and addresses, currency, risk limits, and payment terms. Append-only debit/credit movements calculate per-account balances. Reversals append linked opposite-direction entries; risk limits are checked transactionally for customer debit movements. Dated statements include opening balance, period movements, running balance, totals, and closing balance. CSV export and local CSV comparison do not import or change ledger records. Each tenant has a base currency (existing tenants default to TRY); TenantAdmins can change it only before currency rates or operational financial/quote records exist. Admin-entered exchange rates are tenant-scoped, dated, append-only revisions: one foreign-currency unit maps to base-currency units. Rate entry is manual and records an optional source; the base currency is always 1 and has no row. Groups support listing and creation. Finance also reports open invoice exposure by currency, comparing outstanding balances at invoice-date and current rates in the tenant base currency. This is a read-only estimate: it does not post a journal entry or realize foreign-exchange gains/losses. Period-end FX revaluation journals remain pending.

### Sales

Sales supports quote draft, send, accept/reject, single-conversion sales orders, warehouse reservations for open order quantities, partial delivery notes, and transactional warehouse stock issue. Reservations reduce available warehouse stock and are consumed by deliveries from the assigned warehouse; TenantAdmins can release remaining reservations with a reason. Manual issues, transfers, supplier returns, and receipt reversals preserve active reservations. Voiding a delivery restores its reservation if that reservation is still active. A posted delivery can create one invoice. Posting records the customer debit and checks the risk limit. Invoice voids preserve the ledger through a linked credit reversal. Invoice details support partial/full collections allocated to an invoice; posting creates a customer credit, while voiding appends a linked debit reversal and restores the invoice balance. Returns can be partial by invoiced line, receive stock into a selected warehouse, and record customer credit. Return voids reverse stock and ledger movements, subject to available unreserved stock.

### Purchasing

Purchasing supports tenant-scoped internal stock requests with separate TenantAdmin approval/rejection; request owners cannot decide their own requests. An approved request can hold submitted supplier quotes with per-line price, discount, tax, validity and supplier currency snapshots. Quote totals are calculated server-side. When a dated tenant exchange rate exists on or before the quote date, totals are converted into the tenant base currency for comparison; missing rates are explicitly left unconverted. The applied rate/date are returned with each quote, and later corrections create a revision without altering the stored quote. A submitted quote can be selected once to create the linked supplier order, and competing submitted quotes are marked not selected. The order copies the requested quantities and quote prices, with tenant-scoped foreign keys tying the order and quote to the same request. Approved requests can still be converted directly when a quote was not collected. Supplier orders also support direct creation, partial/full goods receipts and receipt-linked purchase invoices. Invoice totals snapshot received order pricing; due dates use supplier payment terms. Posting increases the supplier credit balance. Partial supplier payments are capped at the outstanding invoice amount and reduce the supplier balance. Invoice/payment voids preserve the ledger with linked reversals. Receipt voiding requires the invoice and its payments to be voided first. Supplier returns can be partial by invoice line and reduce warehouse stock and supplier payable. Voids append opposite stock and ledger movements. Purchase requests support tenant-scoped text, decimal, date, and boolean custom fields. TenantAdmins define versioned fields; required values are validated at submission, requesters can edit values while a request is awaiting approval, and every value change is append-only with actor and definition-version metadata. Metadata revisions can be reviewed and restored as a new version; prior request values can be restored as a new change while the request remains submitted. Once reviewed, request custom fields are locked with the decision record.

### Stok & Depo

Stock and warehouse records are tenant-scoped. Stock cards use tenant-unique codes and optional unique barcodes, unit codes, categories, and minimum-stock thresholds. Warehouses expose physical, reserved, and available balances for each stock card, including zero balances and below-minimum indicators; a warehouse can be deactivated only at zero physical balance and can later be reactivated. Warehouse code and name edits use SQL Server rowversion to reject stale updates. Receipt and issue movements are append-only; the movement history is paged in batches of 50. Writes lock the warehouse row during transactions to prevent overselling; reversals link opposite-direction movements and cannot make physical or reserved-available stock negative. Multi-line warehouse transfers create paired source/target movements atomically, use tenant-scoped idempotency keys, and can be voided only as a whole when destination stock remains available. Transfer history is paged in batches of 50. Individual transfer legs cannot be reversed separately. Stock-card edits use SQL Server rowversion to reject stale writes. Cards can be deactivated and reactivated; deactivation is blocked while any warehouse has a nonzero balance or an open sales/purchase order line remains. Stock movements snapshot nullable unit costs in tenant base currency. Purchase receipts use order-line price net of line discount and VAT, converted at the receipt-date rate; a missing rate blocks receipt. Manual receipts can state their base-currency unit cost or remain explicitly unvalued. Issues use the current weighted-average cost when all on-hand stock has known cost; returns and reversals carry the source cost, and transfers preserve it across warehouses. The stock view reports known inventory value and unvalued quantity. This is an inventory valuation basis, not a general-ledger posting; landed costs, cost revaluation, unit conversion, and lot/serial tracking remain pending. TenantAdmins can add or deactivate stock-card custom-field definitions (initial metadata revision 1); text, decimal, date, and boolean values are validated and stored per tenant and stock item. Deactivation preserves historical values. TenantAdmins can edit labels and text limits. Every metadata change, deactivation, and restore creates an immutable revision; a prior revision can be restored as a new version. Code and data type are immutable, and changes that would invalidate existing values are rejected. The last 50 value changes per stock-card field are exposed with prior/new values and actor/time metadata; each change is stored immutably with the value update, and restoring a prior value requires explicit confirmation and appends another revision. Required fields are enforced on stock-card creation and value updates; a field can be made required only after existing stock cards have values. Customer accounts also support tenant-scoped custom-field definitions and type-validated values; required customer fields are enforced on card creation and value updates; existing customer cards must be populated before an optional field can be made required. Definitions keep immutable revisions, including a baseline for existing fields; compatible versions can be restored as new revisions. Customer-card values keep append-only history with actor and definition-version metadata; prior values can be restored as new events. Applying custom fields to other ERP entities remains pending.

## Tenant security and persistence

Login is rate limited; passwords use PBKDF2-SHA256 with per-user random salts. Tenant selection verifies membership against PlatformDB and issues a short-lived token containing `tenant_id` and the membership role. Tenant-protected routes derive scope from this verified claim. JWT signing keys and bootstrap credentials are environment configuration only. The current RBAC uses tenant membership roles and project access grants; a fine-grained permission catalog and ABAC policies remain future work.

EF Core is the persistence path. Development can apply migrations on startup when `Database__ApplyMigrationsOnStartup=true`; production startup migration is disabled by default and applies migrations through a controlled release step. A one-time baseline adopts the original `EnsureCreated` schema without dropping data. Audit events are tenant-scoped and append-only; TenantAdmins can review paginated records by date, action, and resource. Audit writes cover authentication, tenant selection, ERP workflows, development requests, and Studio mutations; retention policies and broader mutation coverage remain ongoing work.

## Local run

1. Copy `.env.example` to `deploy/docker/.env` and replace sample secrets.
2. Start the stack with `docker compose --env-file deploy/docker/.env -f deploy/docker/docker-compose.yml up --build -d`.
3. Run the ERP Vite client from `frontend/erp-web` with `npm install` and `npm run dev`; open `http://localhost:5173`.
4. Open Development Studio at `http://localhost:5174`.

`OPENAI_API_KEY` is optional. Set it in `deploy/docker/.env` to enable the Responses API provider; the key is passed only to AI Service and is never stored in the browser.
