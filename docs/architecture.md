# AI ERP Platform: Architecture and Scope

## Architecture decision

Nexora ERP and AI Development Studio run as separate products with separate service boundaries. The ERP Platform API owns authentication, tenant membership, tenant selection, ERP workflows, and platform audit events. AI Development Service owns Studio project metadata, access grants, development requests, approvals, AI-assisted planning and code suggestions, and coordination with the Workspace Runner. The Workspace Runner owns source checkout and tightly scoped filesystem operations. It has no database dependency or Docker socket. A separate `workspace-sandbox` runs explicitly approved test jobs; it does not share the workspace checkout or network with test code.

The target SQL topology is PlatformDB for identity, tenant registry, memberships and catalog data, plus a separate ERP database and a separate AI Studio database for each firm. ERP database names are `AIERPTenant_<tenant-guid>` and Studio names are `AIERPStudio_<tenant-guid>`. The currently deployed/legacy Studio topology is still the shared `AIERPStudio`; do not treat that database as tenant-isolated. Current source routes Studio HTTP requests through tenant-keyed component state and tenant-specific Vault credentials, and rejects the legacy shared state. The provisioning Worker now creates per-tenant ERP and Studio databases, creates their runtime SQL principals, publishes credentials to Vault, and applies migrations. A two-tenant remote disposable acceptance on 2026-10-26 verified fresh ERP + Studio provisioning/migration, Vault-backed own-DB sentinel reads and cross-database denials. That acceptance does not cover production host configuration or existing Studio data. Copy/restore of the legacy shared Studio database into tenant databases remains a separate, unaccepted cutover workflow. Startup isolation guards remain fail-closed unless required provider, AppRole and routing configuration is present; `TenantDatabaseProvisioner.ProvisionAIStudioAsync` rejects shared-database provisioning. Do not infer production deployability from disposable acceptance; see [`release-go-no-go-20261026.md`](release-go-no-go-20261026.md). Setting `Database:SeparationEnabled=true` alone cannot enable the hosts. The deployment/backup/restore release path still needs validated manifests and restore procedures for tenant Studio databases before cutover. Existing backup operations quiesce API/AI writers, verify SQL checksums, and write manifests only after staging files are promoted; restore preserves a safety set. Non-SQL persistent volumes use the writer-quiesced `Backup-PersistentVolumes.ps1` archive workflow. The encrypted rclone mirror copies completed archives and relies on provider lifecycle/versioning for retention. The .env file and encryption keys must remain in an independent secret manager and are not included in volume archives.

## Services and clients

- `AIERP.Api` provides login, tenant selection, ERP endpoints, bootstrap setup, and health checks.
- `AIERP.AIService` provides the tenant-scoped Studio API and calls Workspace Runner using short-lived signed service tokens scoped to one workspace or project and one operation.
- `AIERP.WorkspaceRunner` provisions and inspects checkouts, applies approved single-file changes, and prepares bounded test snapshots. It is not published to the host and has no database or Docker socket.
- `AIERP.WorkspaceSandbox` reads jobs from a private shared queue volume. It has no workspace volume, database, signing key, Docker socket, or network connection.
- `frontend/erp-web` is the authenticated ERP client. `frontend/development-studio` is a separate Vite client served by Nginx on port 5174. Studio authenticates against Platform API and enforces tenant/project permissions through AI Service.

## Tenant permission policies

Tenant membership remains the source of the existing `TenantAdmin` and `TenantUser` roles. The platform permission catalog assigns each authenticated API operation a stable resource/action key across ERP and Studio. Tenant policy rules can allow or deny a role or an individual tenant member and can constrain the decision with request attributes such as role, HTTP action, or a route identifier. Matching deny rules take precedence. `TenantAdmin` remains the tenant-wide administrator and cannot be targeted by tenant policy edits. The access-control API is TenantAdmin-only and audits policy creation and removal.

Existing tenants receive a `TenantUser` baseline matching the prior authenticated-user access, except access-control and audit history; existing endpoint-level administrator checks continue to protect administrative actions. New tenants receive the same baseline at bootstrap. Studio project grants (Viewer, Contributor, Maintainer), tenant filters, ownership checks, and self-review protections remain additional authorization checks. The permission catalog and tenant policies are stored in `PermissionDefinitions` and `TenantPermissionRules`; deploy the `AddTenantPermissionPolicies` migration before using the policy administration screen. The `studio.ai-design` permission catalog entries are deployed by `20261016214200_AddAiUiDesignerPermission`.

## AI Development Studio

Projects are tenant-scoped and register a display name, HTTPS repository URL, and default branch. Tenant administrators register projects; maintainers grant or revoke Viewer, Contributor, and Maintainer access for active members of the same tenant. The last Maintainer cannot be removed. Development requests can be attached to a project and workspace request; approval or rejection is limited to tenant administrators and project Maintainers. A requester cannot approve their own workspace request.

After approval, an authorized Maintainer or TenantAdmin can create a shallow checkout on the configured public HTTPS Git host allowlist (GitHub by default). Repository URLs cannot contain credentials, Git redirects and hooks are disabled, and private or loopback destinations are rejected. The Runner creates a deterministic local `aierp/workspace-<workspace-id>` branch and records the checkout commit. Changes remain in that workspace branch; Studio does not push them or create a pull request.

Project Explorer lists directory metadata and previews UTF-8 text files up to 128 KiB. Its bounded project map uses file names and extensions without reading source contents. Branch status and diffs are separate, explicit read operations. Search results are not automatically sent to AI. A user can select at most five search excerpts for one-time AI analysis after consent; Studio re-reads the exact lines from the authorized checkout and verifies they still match. One explicitly selected Git diff can also be sent for ephemeral review after separate consent. These requests use `store=false`, retain no prompt or source text, and audit only workspace identifiers and operation outcomes.

AI Architect receives a confirmed request and bounded project metadata, not source files. It returns a schema-validated plan that an authorized user may explicitly save. AI Tester can draft manual scenarios from a confirmed request and test-target metadata after AI-sharing consent; these scenarios do not execute. Studio chat sends only the conversation text that the user chose to submit and project/branch names, with no automatic source attachments or tools. Chat messages are retained in the Platform database; users can delete conversations after confirmation.

AI Developer can propose a replacement for one explicitly selected source file (up to 32 KiB) or propose one new file. Sharing existing source requires separate consent. The user reviews a diff and separately approves applying it. Runner checks the original SHA-256, rejects unsafe paths and symlinks, writes atomically, and refuses to overwrite a new-file target. An approved rollback restores prior bytes only while the file still matches the applied hash. Changes, sharing, approval, application, and rollback are audited. AI Developer also supports coordinated proposals for 2–5 explicitly selected source files, with a 64 KiB aggregate input limit. Source-sharing consent is required; every proposed file is reviewed and applied separately through the existing SHA-256 stale-source check, audit, and approval path. No file is automatically applied.

The AI UI Designer accepts a bounded screen brief after explicit AI-sharing consent. It returns a schema-validated declarative plan limited to allowlisted controls, labels, options, layout, and disabled preview actions. Studio renders a safe preview, and the AI Service generates deterministic React/TypeScript from that plan; model-provided executable code and arbitrary HTML are never accepted. No existing source is sent. A Contributor can save the generated .tsx as a new workspace file only after separate explicit confirmation; Runner enforces safe path and new-file rules, and the file is not executed. The operation is gated by the dedicated studio.ai-design permission and audited without retaining the prompt or generated source in the audit record.

Maintainers and TenantAdmins can explicitly create a local commit from the isolated workspace branch. The API requires the current HEAD and selected Studio change IDs; Runner revalidates the full changed-path set, saved change records, and current file hashes. It builds the Git tree/index without invoking hooks or content filters and updates only the isolated local branch. The commit is audited and can then be tested against its clean HEAD; the operation never pushes to the remote repository.

## Test Center and execution sandbox

Test Center discovers likely .NET, Node.js, Python, Go, and Rust targets from bounded manifests and file names. Only discovered `.csproj` projects, `package.json` files with supported native Node test files, Python test files, Go `_test.go` files inside a Go module, and Cargo manifests with Rust test files can currently run, and only after a Maintainer or TenantAdmin confirms execution. The Runner revalidates the selected target, then creates a source-only archive (up to 20,000 files, 100 MiB total, 16 MiB per file). It skips Git metadata, hidden/generated/dependency folders, symlinks, and secret-named paths. The job records the checkout commit, archive SHA-256, and dirty-worktree flag.

The separate sandbox runs fixed commands as UID 65532 with a cleared environment. Maintainers and TenantAdmins can separately build discovered .NET, Node.js, Python, Go, and Rust targets using fixed commands; builds use the same bounded source snapshot and do not modify the checkout. .NET restore uses only NuGet packages baked into the image; unavailable packages are reported without network access. Node.js build runs `node --check` for up to 200 discovered JavaScript files and never executes project modules. Python build runs `python3 -m py_compile` for the selected source file. Go build runs `go build -mod=readonly ./...` with network and toolchain downloads disabled and rejects modules with third-party dependencies. Rust build runs `cargo build --offline` only for standalone packages without external dependency tables or workspaces. These checks do not install project-declared dependencies. Node.js uses the built-in `node --test` runner only. `npm` scripts are never invoked, `node_modules` is excluded, and projects declaring package dependencies are reported unavailable. Python runs the image-provided pytest with no project packages installed; missing imports are reported unavailable. Go runs fixed `go test -mod=readonly .` commands with network and toolchain downloads disabled; modules declaring `require`, `replace`, or `toolchain` directives are reported unavailable. Rust runs fixed `cargo test --offline` commands only for standalone packages without dependency tables or workspace manifests; crate dependencies are unavailable offline. This is a deliberate execution policy: arbitrary dependency installation would run package-manager lifecycle/build code and introduce network supply-chain access into the test boundary. Expanding language support requires an operator-curated, hash-verified offline package cache and an explicit allowlist; the sandbox will not install project-declared dependencies automatically.

The sandbox has no network, Docker socket, database, signing key, or workspace volume. The container uses a read-only root filesystem, drops capabilities except those required by its supervisor, enables no-new-privileges, and is limited to 2 CPUs, 2 GiB memory, and 256 PIDs. Each command has a 90-second total restore/test limit and output is capped. The per-job source snapshot lives on a bounded 2 GiB tmpfs; executable permission is enabled only on that job-temp mount so compiled Go/Rust test binaries can run, while the container root stays read-only. Compiler temporary files stay inside the job directory, which is deleted after execution. The shared queue accepts at most eight outstanding jobs; jobs waiting over 20 minutes or running over 10 minutes expire. Results are retained for up to seven days. Studio checks release readiness by comparing current Git status with successful sandbox evidence for the same clean HEAD. A Maintainer or TenantAdmin can save a release candidate after the API revalidates both facts against Workspace Runner; the append-only record stores the branch, HEAD, test job, target, and snapshot hash and creates an audit event. Candidate records do not create packages or deploy. A TenantAdmin other than the candidate creator can append one approval or rejection with a required note; the API rechecks the candidate commit and sandbox evidence before recording the decision. Decisions cannot be overwritten; a new candidate is needed for another review. A Maintainer or TenantAdmin may assign one immutable SemVer 2 version number to an independently approved candidate after revalidating its clean HEAD and test snapshot. Version strings are unique per project; assignment records the exact commit and audit event and does not create a package or deploy. After approval, a Maintainer or TenantAdmin may request an AI-generated pull request title and description. The API revalidates the clean candidate HEAD and successful test snapshot, and sends only the user-provided summary plus bounded project/branch/commit/test metadata to OpenAI with storage disabled; source files and test output are excluded. The result is an editable draft. Publishing requires a second explicit confirmation and an independent candidate approval. The AI Service requests a short-lived GitHub App installation token scoped to the single repository; the Runner pushes only the exact clean candidate commit, refuses to overwrite a different remote branch, and does not persist the token. The API creates or reuses a draft pull request and audits the result. Configure `GITHUB_APP_ID` and `GITHUB_APP_PRIVATE_KEY_PEM` in the deployment secret store; each publishing action supplies the repository installation ID. GitHub `pull_request` webhook deliveries can synchronize linked candidates’ open, closed, or merged state. Delivery is accepted only with a configured `GITHUB_APP_WEBHOOK_SECRET` of at least 32 UTF-8 bytes and a valid `X-Hub-Signature-256`; the endpoint caps payloads at 1 MiB and is rate-limited. State changes are audited in the Studio database, which is resolved from the shared or separated AI Studio deployment configuration. Configure the same random secret in the GitHub App webhook settings. A Maintainer or TenantAdmin can create one deterministic ZIP for an assigned version after an independent approval and a fresh clean-HEAD/test-evidence check. The Runner excludes hidden/secret paths, symlinks, dependency and generated directories, and enforces file-count and size limits. `AIERP-RELEASE.json` records the commit, version, test snapshot, and each included file hash; package SHA-256 and size are persisted. Authenticated downloads are rechecked against that hash and audited. The local Release Deployer is a separate, internal service. Only the AI Service can call it with a two-minute JWT bound to one tenant, project, deployment, and operation. It reads packages from the Runner’s read-only package volume, verifies the archive SHA-256, manifest, every file hash, size, and path, then creates trusted Compose/Dockerfile definitions; package contents cannot supply deployment configuration. Staging runs as a project-scoped Compose stack with its own SQL Server and persistent data volumes, on an internal Docker network. Only the Studio port is published, bound to host loopback (`localhost`); the staging database and service ports are not published. Each staging service has CPU, memory, and PID limits, and the local host allows at most two active project staging stacks by default. API/AI/Runner containers run as the non-root app user with read-only root filesystems; ephemeral Data Protection and temporary files use bounded tmpfs mounts. The bootstrap password is returned once to the initiating user. Tenant AI provider keys are encrypted in the database using the configured platform encryption key. Local persistent-volume archives are not encrypted and may include source, generated release configuration, and certificate private keys; restrict access to the backup volume and use only the encrypted offsite mirror for remote storage. A staging deploy, redeploy, rollback, and destroy each require a separate explicit user action and are audited.

The Deployer requires the Docker Engine socket, which gives it host-wide container-management power. It is isolated from public ingress, has a read-only package mount, a private service network, a read-only root filesystem, dropped capabilities, and short-lived scope-bound callers. Since Docker socket access itself is not confined by those container controls, this local Compose integration is intended for a trusted development machine. Rollback restarts older application code against the same environment database; it does not reverse schema migrations. Staging and local production Compose stacks use a separate one-shot migrator service, while the API starts with automatic migrations disabled. Production updates require separate user confirmation for deployment and schema migrations; before an update, the Deployer writes a SQL Server backup into the separate persistent `aierp-production-backups` Docker volume and verifies that the file is visible through its own read-write mount before proceeding. A one-shot Compose initializer sets the shared backup-volume root to SQL Server UID 10001 before the database starts; generated staging and production stacks apply the same setup. The SQL data and backup volumes are distinct but both remain on this host. The Release Deployer also refreshes each active Production database set daily at 02:00 UTC and makes the staged, verified set the active release's restorable snapshot. The optional `offsite-backup` Compose profile mirrors snapshots to an S3-compatible target with rclone client-side crypt encryption and no remote pruning, then verifies remote contents by downloading and comparing. Set provider-side versioning/lifecycle retention and periodically test the documented offsite restore. After a failed release, the Deployer attempts to restart the previous application stack and health-checks it when Compose starts successfully; the result is written only to Deployer logs. A TenantAdmin can request an audited restore of the current release's database snapshot together with its recorded application package. The Deployer verifies the full database set, creates a verified safety backup of the current databases, stops writers, restores the selected set with checksums, starts the matching application, and health-checks it. If the target application fails, it attempts to restore the safety backup and restart the current application; that recovery result is written to Deployer logs.

After a successful staging deployment, a Maintainer can submit a reasoned production-promotion approval request. Only a different TenantAdmin may approve or reject it, and the decision and notes are audited and immutable. Approval alone does not start deployment. A different TenantAdmin must separately confirm the local production deployment and, in a second confirmation, authorize schema migrations. The selected production target is this machine’s Docker Compose. Production is bound to localhost on a separate port, uses a persistent SQL data volume and the separate `aierp-production-backups` volume, and the Deployer attempts to restart the prior application package when an update fails, then health-checks it if Compose starts successfully. The first bootstrap password is shown to the initiating administrator once. The optional `public-ingress` profile exposes only Development Studio through Caddy; generated Production stacks remain loopback-bound. The Compose architecture remains single-host and has no HA profile; HA requires an external failover-capable database, replicated storage, coordinated application orchestration/routing, and a compatible deployment control plane; Production history exposes a destructive restore for the active release or a failed release when its previous app package and pre-deployment backup are recorded; a typed backup-deployment-ID confirmation is required.

### Availability, deployment, and recovery boundary

**Supported today:** Local Compose and generated staging/production stacks run on one Docker host. Named SQL, workspace, package, Deployer-state, and backup volumes persist across container replacement on that host. Restart policies can restart local containers; SQL health checks query the local instance. Production schema changes use a separate migration step. Release updates make a verified SQL backup before deployment; the Deployer also attempts to refresh each active Production database set daily at 02:00 UTC, quiescing the API and AI Service during capture. Optional offsite backup copying encrypts and verifies uploaded backup objects. Failed releases can restart the prior application package; an authorized restore verifies the selected database set, makes a safety backup, restores it, then starts the matching package. Application rollback alone does not reverse schema migrations.

The optional local Prometheus profile scrapes Platform API, AI Service, IntegrationHost, and Release Deployer. IntegrationHost is reachable by Prometheus only through the dedicated internal `integration-metrics` network; other scrape targets use the internal `monitoring` network. Their `/metrics` endpoint exports request-duration histograms with bounded method, route-template, and status labels; request paths, query strings, tenant IDs, and user IDs are not labels. AI assistant tool counters and duration histograms expose only an allowlisted tool name and outcome. Integration adapter execution counters and duration histograms expose outcome only; integration codes, tenant IDs, payloads, correlation IDs, and provider references are excluded. Both business telemetry meters are bridged through a narrow allowlist and bounded labels. The UI is published only on host loopback at port 9090, and the TSDB retains at most 15 days or 2 GB. The included rules detect scrape outages and sustained 5xx rates, but there is no Alertmanager or external notification destination. These settings are development observability, not an operator alerting service-level objective. Runtime scrape acceptance is pending a healthy Docker Engine; see the IntegrationHost README for the verification steps and expected series.

**Not supported today:** Automatic host or SQL failover, multi-host service replicas and health-aware traffic routing, or shared/replicated volumes. API and AI Service readiness probes check their configured databases, but they do not provide cluster-wide dependency orchestration or traffic draining. Architecture decision: Nexora Compose remains a single-host deployment; HA is an external infrastructure project and is not simulated with multiple containers on one host. Generated Production Compose provisions a per-project local SQL Server; it has no external SQL endpoint setting. Release Deployer uses the host Docker socket and a persistent file lock shared by replicas on the same local Docker host. That lock serializes deploy, restore, cleanup, and scheduled backup operations and is released by the OS if a process exits. It is not a multi-host lock; replicas on separate hosts or volumes remain unsupported. The daily backup is a recovery point, not database replication or a guaranteed RPO; offsite copy is asynchronous and provider retention is external. A host outage can interrupt service until infrastructure is recovered, and local volumes/backups are lost with the host.

**Recorded deployment decision:** Keep the supported product topology single-host Compose and do not claim HA. The following are prerequisites for a future, separately scoped HA deployment; they cannot be completed in this repository without a selected provider, service-level objectives, and target environment:

- [ ] Select the hosting/provider topology, SQL failover service, stable database endpoint, and supported SQL edition/licensing.
- [ ] Set service-level RPO/RTO; choose PITR/backup frequency, offsite retention, and verify restore/failover drills against those targets.
- [x] Local readiness contract implemented: API checks PlatformDB; AI Service checks PlatformDB and its configured Studio database. This does not implement cluster routing or graceful draining.
- [x] Persistent data ownership and single-writer boundary documented: SQL Server owns database state; Workspace Runner owns workspace/job/package volumes; Release Deployer owns staging/production release state and SQL backup snapshots; Caddy owns certificate/config volumes. Release Deployer, Workspace Runner, SQL Server, and the sandbox queue remain single-instance. Non-SQL volumes use the quiesced archive/restore workflow; SQL databases use checksum-verified SQL backups. API keys, signing/encryption keys, and the Compose `.env` remain in an independent secret manager.
- [ ] Replace the host-socket Deployer flow with a shared-state deployment controller and multi-host distributed locking; the persistent-volume lock serializes single-host Compose replicas only. Confirm exactly one migration job per release and backward-compatible schema changes before traffic shifts in a multi-host environment.
- [x] Local single-host request and allowlisted assistant/integration business metrics, a loopback-only Prometheus UI, bounded retention, and scrape/error alert rules are configured through the optional `monitoring` Compose profile; runtime scrape acceptance remains pending.
- [ ] Configure a secret manager, external alert delivery, failure domains, and operational runbooks for the selected environment, then prove database failover and application recovery in a test environment.

These are external deployment tasks, not features enabled by a Compose profile. For schema rollback, the Deployer intentionally restores the matching pre-release database backup together with the prior application package; it never automatically downgrades EF migrations. If a migration must be reversed, stop writes, take and verify a fresh SQL backup, restore the pre-migration database set through the controlled restore flow, and then start the matching application version. Persistent-volume recovery uses the separately documented, writer-quiesced archive workflow. Backup snapshots are retention-based recovery points; operators must monitor the existing Deployer/offsite job logs and schedule restore drills because this repository has no alerting destination or service-level RPO/RTO configured.

Contributors can request AI analysis for a failed or incomplete sandbox test/build after explicit confirmation. The AIService re-reads the job from Workspace Runner, masks common API keys, bearer tokens, credential assignments, and URL credentials, and sends at most 16,000 characters of log output with bounded job metadata to the configured provider. The AI returns a structured likely cause, human-reviewed next steps, and limitations; it cannot execute commands or apply fixes. Raw job output and analysis are not persisted by this endpoint; only request/completion audit metadata is stored.

## ERP modules

## Tenant custom forms and workflows

Custom forms are tenant-owned records persisted through `TenantDbContext`, so they follow the existing shared or per-tenant database routing. TenantAdmins define a draft with up to 40 typed fields (text, decimal, date, boolean, or declared choice), publish versions, inspect revision history, restore a prior revision into a draft, and create a new draft from a published version. Users submit only against the currently published form. The API validates and normalizes each value, stores a snapshot of the exact schema and version with the submission, and exposes the submitter's own responses; TenantAdmins can review tenant responses and approve or reject with a reason.

Reusable workflows are also tenant-owned. TenantAdmins publish definitions with up to 20 ordered approval steps assigned to TenantAdmin, TenantDeveloper, or TenantUser. Users start an instance against a business record descriptor; the engine snapshots definition version, approval steps, and bounded string context so later definition changes do not alter in-flight work. Only the current step's role (or a TenantAdmin) can decide; the requester cannot decide their own instance. Decisions are audited, SQL rowversion rejects concurrent advancement, and a filtered unique index ensures only one published version exists per tenant and workflow code. Both forms and workflows use tenant-scoped records and have PlatformDbContext and TenantDbContext migrations.

TenantAdmins can publish business rules for `purchase-request.submitted`, `sales-quote.accepted`, and `purchase-order.created`. Each rule combines up to 20 typed conditions over that event's allowlisted facts and selects a published approval workflow. Rule evaluations and workflow-instance creation are persisted together. A matching purchase-request rule blocks the manual approval route until the workflow is decided; a matching sales-quote rule blocks conversion while approval is pending. A matching purchase-order rule marks the order `PendingApproval` before it can be edited or received; approval returns it to `Open`, while rejection leaves it blocked. Decisions lock the linked business record, update its state in the workflow transaction, and are audited. Each evaluation is retained with a match result and workflow link.

The tenant report builder exposes fixed customer-account, sales-invoice, sales-order, purchase-order, purchase-receipt, purchase-request, stock-card, and (TenantAdmin-only) workflow-history datasets. Definitions select catalog columns, combine up to eight typed filters, use stable sorting, and page up to 200 rows. Reports support one-to-three-field SQL grouping, source-specific count/sum/average aggregates, and typed group-to-detail drill-down. Monetary invoice and purchase-order aggregates require grouping by currency or an exact single-currency filter. Purchase-receipt detail supports tenant-scoped supplier, warehouse, status, date and quantity filters with bounded CSV export; it intentionally does not group receipt rows. Purchase-request reports also apply the purchasing status/owner ABAC filter. Workflow history exposes workflow and business-record metadata only; it never returns the serialized workflow context, and both catalog discovery and query execution restrict this source to TenantAdmins and the selected tenant. TenantAdmins can persist shared tenant report definitions; dynamic list definitions are stored as a distinct view kind and cannot group. CSV export reruns the filtered query server-side, caps detail and grouped exports at 10,000 rows, escapes CSV values and neutralizes formula-like text prefixes. Report runs, exports, and definition changes are audited. The catalog does not expose arbitrary SQL or entity names. Additional operational report sources and SQL Server acceptance coverage remain future Phase 3 work.

## Extension SDK boundary

`AIERP.ModuleSDK` defines a declarative module manifest for code, version, dependencies, permissions, menu entries, and checksummed migrations. The validator rejects malformed identifiers and versions, self or duplicate dependencies, unsafe/non-local routes, undeclared menu permissions, and invalid migration checksums. Its dependency resolver checks the requested dependency closure, minimum SemVer versions, missing packages, and cycles, then returns a deterministic dependency-first install order. Package verification checks a bounded artifact SHA-256 and RSA-PSS publisher signature against a host-provided trust resolver without extracting or loading executable code. The manifest contains no executable assembly path or shell command. `AIERP.IntegrationSDK` defines tenant-scoped adapter context with correlation and idempotency keys, bounded retry policy, typed results, a deadline-aware retry executor, and secret references for a host-owned resolver. Retries preserve the same idempotency key and adapter exception messages are not returned. Durable queueing, idempotency deduplication, secret resolution, and vendor adapter hosting are not implemented yet.

The platform module catalog now persists publisher trust keys, signed release metadata, artifact hashes, and draft/published/revoked status. A platform super-admin manages publisher keys and platform developer/release-manager roles; developers can upload bounded signed ZIP packages, while a separate release manager or super-admin approves publication. A runnable package is a signed ZIP with exactly one root `module.wasm` (maximum 8 MiB); the API verifies the publisher signature and content hash before storage and extracts only that WASM file into a content-addressed package volume. The initial super-admin is assigned to `Platform:SuperAdminEmail` (defaults to `Bootstrap:Email`) when the configured account exists. Set the email deliberately in deployment configuration.

The ERP Marketplace lists the latest published catalog release for each module. A TenantAdmin can add a published version to the tenant’s module entitlement list; activation validates its signed catalog manifest and all declared dependency versions against other enabled tenant modules. Upgrades are refused when they would invalidate an enabled dependent; removal is refused while another enabled module depends on the target. These actions are tenant-scoped and audited. The separate .NET PluginHost validates and executes Core WASM modules through a JSON ABI (`aierp_alloc(i32) -> i32`, `aierp_invoke(i32, i32) -> i64`) with a required exported memory. All imports are rejected; modules get no WASI, filesystem, network, ERP database, or host callbacks. Each invocation is authorized by the API using a short-lived token bound to one tenant, module, version, artifact hash, and operation. The runtime limits linear memory to 64 MiB, fuel to 20 million instructions, stack to 1 MiB, input to 256 KiB, and output to 512 KiB. API and PluginHost use a separate signing key, and Compose keeps the host on an internal network with read-only package access, read-only root, no Linux capabilities, and CPU/memory/process limits. Activated manifest menu entries appear in ERP navigation and invoke the matching WASM action in a generic JSON screen. The API binds each menu entry to its declared module permission, exposes active module permissions in the tenant ABAC editor, filters menu entries by that permission, and checks the permission again on invocation; generic `erp.tenant-modules.execute` authorization remains an additional gate. Manifest routes remain metadata and the guest UI is currently a JSON invocation form. No ERP data or integration capabilities are exposed to the guest.

Integration SDK retry orchestration now exists, but there is still no persistent job queue/idempotency store, external adapter host, production secret resolver, or configured vendor connector. Lifecycle health reporting and integration runtime telemetry also remain open. Tenant-scoped module data capabilities and manifest-driven form/table UI are implemented for the fixed operations listed in `src/Extensions/AIERP.ModuleSDK/README.md`; the WASM ABI and package signing workflow are documented there as well.

### Cari

Cari provides tenant-scoped customer and supplier account cards, search, pagination, detail, create/update, and activate/deactivate. Codes are uppercase and unique per tenant. SQL Server rowversion protects concurrent updates. Accounts support tenant-owned groups and addresses, currency, risk limits, and payment terms. Append-only debit/credit movements calculate per-account balances. Reversals append linked opposite-direction entries; risk limits are checked transactionally for customer debit movements. Dated statements include opening balance, period movements, running balance, totals, and closing balance. CSV export and local CSV comparison do not import or change ledger records. Each tenant has a base currency (existing tenants default to TRY); TenantAdmins can change it only before currency rates or operational financial/quote records exist. Admin-entered exchange rates are tenant-scoped, dated, append-only revisions: one foreign-currency unit maps to base-currency units. Rate entry is manual and records an optional source; the base currency is always 1 and has no row. Groups support listing and creation. Finance reports open invoice exposure by currency and allows TenantAdmins to create one immutable, balanced period-end FX revaluation voucher per date. The voucher snapshots each open foreign-currency sales and purchase invoice, its outstanding amount, invoice-date and closing rates, and the incremental base-currency adjustment since the prior voucher; missing rates block creation. Receivable and payable gains/losses are represented as balanced control-account and FX gain/loss lines, and subsequent vouchers reverse prior adjustments when balances are settled or reduced. Vouchers are tenant-scoped, audited, and available for review in Finance. The general ledger currently provides a tenant-configurable account list and mappings for sales and purchase invoices, sales deliveries and returns, supplier returns, customer collections and supplier payments using cash/bank accounts or card/check clearing mappings, FX revaluation, and inventory cost adjustments. TenantAdmins can transfer these sources into balanced, immutable journal entries, with duplicate source-transfer protection and account validation. Collection and payment cash/bank accounts have individual tenant mappings; card/check transactions use configurable clearing/portfolio mappings. Sales invoice transfer debits receivables and credits net revenue and calculated tax; purchase invoice transfer credits payables and debits net cost and recoverable tax. Foreign-currency invoice, return, collection, and payment transfers use the latest tenant rate on or before the source date, and the rate is recorded in the journal description. TenantAdmins can also create immutable manual entries after server validation that all lines use active tenant accounts and debit/credit totals balance. Any manual or transferred source entry can be reversed once by an immutable balancing entry with a required reason. A transferred source must be reversed before its operational record can be voided. The ledger entry list is tenant-scoped and paginated, and the ledger provides a date-filtered trial balance with per-account debit/credit movements and balances. Sales and purchasing invoice posting remains a TenantAdmin-initiated transfer; collections and payments require an explicit TenantAdmin transfer; sales delivery transfers debit sold-goods cost and credit inventory using the posted stock cost snapshot. Purchase receipts debit inventory and credit a configured goods-received-not-invoiced account; the related invoice clears that balance and posts any net-cost difference. Return transfers post the counterparty, revenue/cost, and tax adjustment, plus the related inventory and cost-of-goods movement from the return stock movements; missing stock-cost snapshots block transfer. Posted entries currently cover sales and purchase invoices, returns, linked collections/payments, FX revaluation, inventory-cost movements, sales deliveries, and purchase receipts.

### Sales

Sales supports quote draft, send, accept/reject, single-conversion sales orders, warehouse reservations for open order quantities, partial delivery notes, and transactional warehouse stock issue. Reservations reduce available warehouse stock and are consumed by deliveries from the assigned warehouse; TenantAdmins can release remaining reservations with a reason. Manual issues, transfers, supplier returns, and receipt reversals preserve active reservations. Voiding a delivery restores its reservation if that reservation is still active. A posted delivery can create one invoice. Posting records the customer debit and checks the risk limit. Invoice voids preserve the ledger through a linked credit reversal. Invoice details support partial/full collections allocated to an invoice; posting creates a customer credit, while voiding appends a linked debit reversal and restores the invoice balance. Returns can be partial by invoiced line, receive stock into a selected warehouse, and record customer credit. Return voids reverse stock and ledger movements, subject to available unreserved stock. Sales quotes support tenant-scoped typed custom fields. TenantAdmins can create, version, deactivate, and restore definitions; required values are checked when creating a draft and while editing it. Values and actor/time history are committed together, and draft-only restores append a new value event. Sent and later quote statuses lock custom-field edits. Sales orders have their own tenant-scoped typed custom fields. Matching active field codes copy quote values into the order during conversion; missing required values block conversion. Open orders allow audited value changes and restores; completed or cancelled orders are immutable. TenantAdmins manage order definitions, and required-field changes validate all open orders.

### Purchasing

Purchasing supports tenant-scoped internal stock requests with separate TenantAdmin approval/rejection; request owners cannot decide their own requests. An approved request can hold submitted supplier quotes with per-line price, discount, tax, validity and supplier currency snapshots. Quote totals are calculated server-side. When a dated tenant exchange rate exists on or before the quote date, totals are converted into the tenant base currency for comparison; missing rates are explicitly left unconverted. The applied rate/date are returned with each quote, and later corrections create a revision without altering the stored quote. A submitted quote can be selected once to create the linked supplier order, and competing submitted quotes are marked not selected. The order copies the requested quantities and quote prices, with tenant-scoped foreign keys tying the order and quote to the same request. Approved requests can still be converted directly when a quote was not collected. Supplier orders also support direct creation, partial/full goods receipts and receipt-linked purchase invoices. Invoice totals snapshot received order pricing; due dates use supplier payment terms. Posting increases the supplier credit balance. Partial supplier payments are capped at the outstanding invoice amount and reduce the supplier balance. Invoice/payment voids preserve the ledger with linked reversals. Receipt voiding requires the invoice and its payments to be voided first. Supplier returns can be partial by invoice line and reduce warehouse stock and supplier payable. Voids append opposite stock and ledger movements. Purchase requests support tenant-scoped text, decimal, date, and boolean custom fields. TenantAdmins define versioned fields; required values are validated at submission, requesters can edit values while a request is awaiting approval, and every value change is append-only with actor and definition-version metadata. Metadata revisions can be reviewed and restored as a new version; prior request values can be restored as a new change while the request remains submitted. Once reviewed, request custom fields are locked with the decision record. Purchase orders also support tenant-scoped typed custom fields. Direct order creation validates required values, and request conversion copies matching field codes while allowing order-only required fields to be completed; open and partially received orders remain editable, while received or cancelled orders are locked. Values retain append-only actor, timestamp, and definition-version history. Supplier quotes also support tenant-scoped typed custom fields. Required values are checked when a submitted supplier quote is created; values remain editable only while the quote is under evaluation, and selected or unselected quotes are locked. When a supplier quote is selected for an order, matching active field codes copy its values to the order and take precedence over request values.

### Üretim

Manufacturing uses tenant-scoped, immutable bill-of-material definitions and planned production orders. A recipe records its finished stock item, output yield, unique component rows with scrap percentages, and optional ordered work-center operations. Creating an order snapshots component quantities and labels plus operation durations and hourly base-currency labor/overhead rates so later recipe or rate changes cannot rewrite the plan. Work centers have daily minute capacities. Capacity scheduling locks work centers in stable order, allocates each operation across available days while preserving route sequence, persists daily reservations, and rejects plans that cannot fit within one year; an order with a route cannot be released until all operations have a schedule. Cancelling a planned/released order frees its capacity allocations. Each released operation must be started and completed in route order before the production order can complete. Completion records actual setup and run minutes, calculates labor and overhead using the hourly rates snapshotted on the production order, and rolls actual operation cost into the finished-goods cost. Orders transition from Planned to Released to Completed, or can be cancelled before completion; transitions are audited and completion is idempotently blocked. Completion serializes the order mutation in SQL Server, locks the warehouse and stock items, checks available component balances after active sales reservations, then records component issues and finished-goods receipt in one database transaction. Weighted-average component costs are rolled into the finished-goods receipt when all component costs are known; incomplete historical costs are reported and the receipt remains explicitly uncosted. Lot-tracked components are consumed automatically in FEFO order; expired lots are skipped. Serial-tracked components are consumed one code per unit in ascending serial-code order, and each issue movement stores its trace allocations. For tracked finished goods, the operator supplies the output lot code and expiry date or one unique serial code per unit during completion; lot expiry values must remain consistent for a reused lot code. Output trace rows are stored on the finished-goods receipt, and duplicate serials, expired lots and mismatched allocation totals are rejected. The MRP plan starts from open sales-order backlog plus dated extra demand, subtracts posted deliveries and selected-warehouse reservations, and recursively explodes active recipes. Stock cards carry procurement and manufacturing lead-time days; purchase orders can carry an expected receipt date and target warehouse. Dated inventory, purchase orders and scheduled/open production are consumed only when their supply date is no later than each demand date. Make/buy recommendations include required-by and release/order dates, with dependent component demand moved back to the planned manufacturing start and purchase timing calculated from procurement lead time. Open sales orders can store an audited required delivery date; orders without one conservatively use the plan date. Legacy purchase orders without date or target warehouse are excluded from dated supply. Active recipe ambiguity/cycles are rejected and expansion is bounded. Recommendations are persisted as tenant-scoped snapshots and can be explicitly converted to planned manufacturing orders and submitted purchase requests; sector-specific workflows and live SQL Server execution remain open.

Stock and warehouse records are tenant-scoped. Stock cards use tenant-unique codes and optional unique barcodes, unit codes, categories, and minimum-stock thresholds. Warehouses expose physical, reserved, and available balances for each stock card, including zero balances and below-minimum indicators; a warehouse can be deactivated only at zero physical balance and can later be reactivated. Warehouse code and name edits use SQL Server rowversion to reject stale updates. Receipt and issue movements are append-only; the movement history is paged in batches of 50. Writes lock the warehouse row during transactions to prevent overselling; reversals link opposite-direction movements and cannot make physical or reserved-available stock negative. Multi-line warehouse transfers create paired source/target movements atomically, use tenant-scoped idempotency keys, and can be voided only as a whole when destination stock remains available. Transfer history is paged in batches of 50. Individual transfer legs cannot be reversed separately. Stock-card edits use SQL Server rowversion to reject stale writes. Cards can be deactivated and reactivated; deactivation is blocked while any warehouse has a nonzero balance or an open sales/purchase order line remains. Stock movements snapshot nullable unit costs in tenant base currency. Purchase receipts use order-line price net of line discount and VAT, converted at the receipt-date rate; a missing rate blocks receipt. Manual receipts can state their base-currency unit cost or remain explicitly unvalued. Issues use the current weighted-average cost when all on-hand stock has known cost; returns and reversals carry the source cost, and transfers preserve it across warehouses. The stock view reports known inventory value and unvalued quantity. TenantAdmins can allocate landed costs to posted purchase receipt lines by extended value, quantity, or equally; allocations retain source receipt, line, warehouse, quantity, and cost snapshots, and the receipt cannot be voided until its landed costs are reversed. TenantAdmins can post signed, append-only cost revaluation adjustments for a warehouse/item balance; each can be reversed with a linked opposite adjustment, and adjustments cannot make the inventory value negative. Both flows update inventory valuation and future weighted-average issue cost without changing physical quantity; they do not post to a general ledger. Stock cards can define tenant-scoped alternate units with a positive factor to their base unit. Manual stock receipts/issues, sales quotes, purchase requests, direct purchase orders, warehouse transfers, receipts, deliveries, and returns accept configured alternate units. The API validates the conversion and supported decimal precision, then stores operational quantities and prices in the stock card base unit; movement and transfer records retain entered-unit snapshots where those fields are modeled. Landed-cost allocation uses the receipt’s base-unit quantities or extended costs. Stock cards can also track no identifier, lots, or serial numbers. Tracked receipts require codes whose allocated base-unit quantities equal the movement; lots retain an expiry date and serial allocations are one unit each. Manual issues validate submitted allocations against available tracked quantities; transfers, deliveries, and supplier returns select stock by earliest expiry then code. Transfer legs and all void reversals retain the same allocations. Sales returns restore the original delivery's lot/serial allocations. Movement history exposes trace codes and expiry dates. A stock card's tracking mode cannot change after inventory movement history exists. TenantAdmins can add or deactivate stock-card custom-field definitions (initial metadata revision 1); text, decimal, date, and boolean values are validated and stored per tenant and stock item. Deactivation preserves historical values. TenantAdmins can edit labels and text limits. Every metadata change, deactivation, and restore creates an immutable revision; a prior revision can be restored as a new version. Code and data type are immutable, and changes that would invalidate existing values are rejected. The last 50 value changes per stock-card field are exposed with prior/new values and actor/time metadata; each change is stored immutably with the value update, and restoring a prior value requires explicit confirmation and appends another revision. Required fields are enforced on stock-card creation and value updates; a field can be made required only after existing stock cards have values. Customer accounts also support tenant-scoped custom-field definitions and type-validated values; required customer fields are enforced on card creation and value updates; existing customer cards must be populated before an optional field can be made required. Definitions keep immutable revisions, including a baseline for existing fields; compatible versions can be restored as new revisions. Customer-card values keep append-only history with actor and definition-version metadata; prior values can be restored as new events. Warehouses also support tenant-scoped typed custom fields. TenantAdmins manage definition versions, deactivation, and compatible restores; values are validated, required values are enforced during depot creation and updates, and changes retain actor/time history with explicit-confirmation restore. Making a field required or tightening its text limit is blocked until existing warehouse values comply.

## Tenant security and persistence

Login is rate limited; passwords use PBKDF2-SHA256 with per-user random salts. Tenant selection verifies membership against PlatformDB and issues a short-lived token containing `tenant_id` and the membership role. Tenant-protected routes derive scope from this verified claim. JWT signing keys and bootstrap credentials are environment configuration only. Authorization uses tenant membership roles and project access grants, plus a route/method permission catalog for read, create, update, delete, and execute actions. TenantAdmins can create tenant-scoped Allow/Deny rules for non-admin roles or individual members, optionally conditioned on supported subject, request, and resource-route attributes with Equals, NotEquals, or In matching. Deny rules take precedence; TenantAdmin access remains protected from policy lockout. Attribute conditions use supported subject, request, route, and resource attributes. For single-record ERP routes, `resource.status` is resolved from the tenant-scoped sales quote, sales order, purchase request, purchase order, sales invoice, or purchase invoice before applying the rule. Customer detail and balance routes resolve `resource.customerId`, `resource.customerType`, and `resource.customerActive` from the tenant-owned customer account. The `resource.status` condition and the related `resource.customerId`, `resource.supplierId`, and `resource.ownerUserId` conditions are applied per row before counting and paging on the corresponding sales quote/order/invoice, purchase request, purchase order, and purchase invoice collections. Related attributes are also resolved for their single-record routes. Collection rules fail closed when they depend on a resource attribute that the collection does not expose.

EF Core is the persistence path. Development can apply migrations on startup when `Database__ApplyMigrationsOnStartup=true`; production startup migration is disabled by default and applies migrations through a controlled release step. A one-time baseline adopts the original `EnsureCreated` schema without dropping data. Audit records are tenant-scoped where applicable and append-only; TenantAdmins can review paginated records by date, action, and resource without exposing linked user email addresses. API writes sanitize resource text and record tenant entity mutations with resource type/count metadata when a workflow does not already create a specific event. Login and tenant-selection failures are recorded using generic outcomes, without submitted credentials or tenant identifiers. TenantAdmins can configure retention from 30 to 3650 days (default 365); a daily 02:00 UTC worker calls a SQL Server procedure that removes expired records in bounded batches, records the purge count and cutoff, and updates the tenant's last-purge timestamp. A database trigger rejects audit updates and deletes outside that procedure. Tenantless authentication events use a 365-day retention period.

Tenant database isolation is mandatory at runtime. The legacy shared database is supported only as an offline migration source; setting a flag alone never migrates data. Before a tenant copy starts, the migrator requires `Database:SeparationBackupPath` to point to a full backup of the configured Platform database that passes `RESTORE VERIFYONLY WITH CHECKSUM`, contains a backup checksum, and is no more than 30 minutes old and the newest full backup recorded by SQL Server. Stop all writers before taking that backup. Production deployment quiesces the API and AI Service, creates and verifies the full backup set, and passes the PlatformDB backup path to the migrator. For local Compose, set `DATABASE_SEPARATION_ENABLED=false` only as an explicit legacy-source marker, then run `powershell -ExecutionPolicy Bypass -File deploy/docker/Enable-TenantDatabaseSeparation.ps1 -Apply -PurgeLegacyTenantData`; Compose still launches current application code in mandatory isolated mode. The script stops both writers, creates and verifies backups, copies and verifies the separated databases, then—only with the explicit purge switch—creates a fresh post-copy backup, previews table/row counts, purges and verifies the legacy operational rows, and starts the isolated services. Without the purge switch it leaves both services stopped and cutover incomplete. The migrator provisions one deterministic tenant database per existing tenant, applies separate TenantDbContext and AIStudioDbContext migrations, and copies matching rows transactionally with IDs preserved. It compares source and destination row counts table by table and checks foreign-key constraints before marking a database ready. The operator-only `--legacy-tenant-data-purge-preview` reports table and row counts without data values. `--purge-legacy-tenant-data` requires a literal confirmation argument, all tenant catalog entries and AIERPStudio Ready, source/destination exact per-tenant row-value comparison across every comparable non-computed, non-rowversion column, and a fresh verified backup. It holds source and destination table locks from comparison through purge, then transactionally removes only registered tenant rows from tables mapped by TenantDbContext, preserves platform identity/catalog metadata, sets the append-only audit retention session context only during that transaction, verifies constraints, and commits only when all tenant-scoped operational tables in the live Platform database are empty. The preserved backup remains an offline recovery artifact and contains the former rows; it is not an active operational database. Provisioning is idempotent: `Ready` databases are never recopied, while interrupted, not-ready copies can be retried after producing a fresh backup. After provisioning, `dotnet AIERP.Api.dll --verify-separation` checks catalog readiness, database availability, and trusted foreign keys. Production and staging use separate SQL logins for PlatformDB and tenant/Studio data access; the migrator and Deployer retain the SQL administrator credential for DDL, cross-database copy, and backup/restore operations. The runtime logins receive data-reader/writer roles only on the databases they need.

## Integration execution boundary

ERP integration calls use a separate `AIERP.IntegrationHost`; ERP modules and the browser never receive provider credentials or direct provider network access. The Platform API requires the tenant `erp.integrations.execute` permission, validates the integration code, JSON-object payload (128 KiB maximum), and `Idempotency-Key`, audits only the provider code and outcome, and forwards a 30-second internal JWT bound to the user, tenant, integration and operation. The host accepts only the `AIERP.Api` service claim and `integration.execute` operation.

The current adapter is a generic JSON-over-HTTPS POST. Operators must explicitly enable an adapter and configure its HTTPS base URL, relative path and exact `AllowedHosts` entry. Optional `RequestMappings` transform selected dot-separated JSON object paths into a bounded provider payload; when mappings are configured, unmapped fields are omitted and required fields are checked before any outbound call. Without mappings, the original JSON payload is passed through for compatibility. Redirects and cookies are disabled; provider payloads and responses are capped at 128 KiB. Credentials are optional tenant-specific files under `deploy/docker/integration-secrets/<tenant-guid>/<secret-name>` and are mounted read-only. Do not put provider keys in browser code, integration payloads, or Compose variables. This directory is git-ignored. The service runs non-root, with a read-only root, no Linux capabilities, resource limits, no published host port, and separate internal-runtime and outbound networks; it does not receive the Docker socket.

The Platform API writes each request into `IntegrationOperations` before acknowledging it. Request and result JSON use AES-GCM encryption with tenant, operation and purpose bound as authenticated data; `INTEGRATION_QUEUE_ENCRYPTION_KEY` must remain stable and be backed up securely. The client idempotency key is hashed before storage, and a tenant/integration unique index prevents duplicate work for 30 days. Reusing the key with a different payload returns 409. `POST /api/integrations/{integrationCode}/execute` returns 202 and an operation ID; `GET /api/integrations/operations/{operationId}` requires the integration read permission and is visible only to the requesting user in the same tenant. The API background worker claims rows with SQL Server `UPDLOCK/READPAST`, retries delivery up to three times with the same tenant-namespaced provider key, and deletes terminal records after the 30-day idempotency window. If a timeout or retryable provider failure leaves the external side effect uncertain, the operation ends as `Indeterminate`; callers must reconcile it with the provider before issuing a new key. This is at-least-once delivery, and duplicate external effects still depend on provider idempotency support.

No adapter is enabled in the checked-in local configuration. The health endpoint reports `configuredAdapters: 0`; queued requests for an absent adapter complete as failed and are never reported as successful. A reconciliation UI, provider-specific mappings/connectors, production credential rotation and live provider verification remain future work. Do not report an external integration as active until its endpoint, credentials, mapping and live verification are configured.

Local Docker Compose runs Platform API with `ASPNETCORE_ENVIRONMENT=Production` so development exception pages cannot return request headers such as bearer tokens. OpenAPI remains development-only. A malformed tenant-selection request with an authenticated bearer was checked locally: it returned HTTP 400 without echoing the token or an Authorization header dump.

## MRP plan snapshots

Successful MRP calculations are saved as tenant-scoped snapshots. The saved JSON preserves the full recommendation lines and source descriptions so later review does not silently recalculate against changed stock or order data. The API lists the latest 100 plans and returns details only to the owning tenant; snapshot creation is audited. A separate explicit, line-selective action revalidates master data before creating planned manufacturing orders and submitted purchase requests. The purchase request remains subject to its configured custom fields, business rules, workflow and approval before it can become a purchase order. Converted indexes are saved to prevent duplicate application; SQL Server conversion runs in a serializable transaction and uses the snapshot row version for concurrent edits.

## Operational report sources

The report catalog includes tenant-scoped purchase receipts, manufacturing orders, inventory movements, bank statements and bank statement lines alongside existing ERP datasets. Receipt reports expose receipt/order/supplier/warehouse, status/date, line count and accepted quantity.
