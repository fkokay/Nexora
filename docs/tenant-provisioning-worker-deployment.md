# Tenant Provisioning Worker deployment wiring

The API company-create route is now asynchronous: authenticated `POST /api/platform/tenants` validates the request and `Idempotency-Key`, then writes the inactive tenant, catalog row and queued job in one Platform transaction. `GET /api/platform/tenants/{tenantId}/provisioning` returns job state; `POST /api/platform/tenants/{tenantId}/provisioning/retry` requeues a failed job. API `--create-company` and `--provision-tenant=<id>` paths fail closed and do not run tenant DDL. The Worker claims leased Platform jobs, provisions and migrates the ERP and per-tenant AI Studio databases, publishes/read-backs their Vault credentials, retries bounded failures, and activates the tenant only after the catalog states are Ready. New-company provisioning creates empty company databases; legacy data copy remains a separately guarded workflow.

The base Compose file contains a separate `tenant-provisioning-worker` service under the opt-in `tenant-provisioning` profile. It has no published port, runs as the non-root user baked into its image, is read-only, drops Linux capabilities, and joins only the SQL/Vault-capable default network. It starts after SQL Server and Platform API report healthy. Worker image labels accept the same OCI revision and version build arguments as the API and AI Service images.

The API and AI Service receive only the Vault tenant SQL **reader** AppRole. Their Platform SQL connection now uses the separate `aierp_platform_runtime` login; it is distinct from the worker provisioning connection and is not granted server-level DDL rights by the staging/release bootstrap. The worker receives both reader and writer Vault AppRoles because it must validate published credentials. Writer credentials and the provisioning SQL connection are mounted only into the worker. The normal Compose stack does not start the worker unless the profile is explicitly selected.

## Required deployment configuration

Supply these values in the protected deployment configuration; do not commit credentials:

- `VAULT_ADDRESS`: HTTPS origin of the Vault server, with no path, query, fragment, or user information.
- `VAULT_MOUNT`: KV v2 mount name; defaults to `secret`.
- `VAULT_TENANT_SQL_READER_ROLE_ID_FILE` and `VAULT_TENANT_SQL_READER_SECRET_ID_FILE`: remote host file paths for the reader AppRole mounted into API, AI Service and worker.
- `VAULT_TENANT_SQL_WRITER_ROLE_ID_FILE` and `VAULT_TENANT_SQL_WRITER_SECRET_ID_FILE`: remote host file paths for the writer AppRole mounted into the worker only.
- `TENANT_PROVISIONER_SQL_CONNECTION_FILE`: remote host file containing the dedicated provisioning SQL connection string, mounted into the worker only.
- `AIERP_PLATFORM_RUNTIME_PASSWORD`: protected Compose environment value for the `aierp_platform_runtime` Platform application login used by API and AI Service. This login must remain limited to Platform application data access; it must not receive server-level database/login creation permissions.
- `DATABASE_SEPARATION_BACKUP_PATH`: SQL Server-side path for the verified Platform backup used during tenant copy.

The Compose file mounts secret files read-only under `/run/secrets`; application configuration references their file paths and reads their contents at startup. Before enabling the Compose profile, verify each configured source with `Test-Path -LiteralPath $path -PathType Leaf` and confirm non-zero length: a missing Docker bind source may appear as an empty directory rather than a file and will cause a startup crash loop. Protect source files on the remote Docker host with operating-system permissions and a controlled rotation process. For the Worker’s non-root UID/GID `1654:1654`, provision the mounted files with owner `root`, group `1654`, and mode `0440`; verify access from the container before enabling the profile. Do not pass RoleId, SecretId, or provisioning SQL credentials as environment values.

The Vault reader policy should be read-only and limited to the KV v2 path `secret/data/tenants/+/sql/*`; the writer policy should be limited to the same path and must not be available to application hosts. Vault `+` matches one tenant-guid path segment. Rotate both AppRole credentials through the organization's secret manager.

## Disposable SQL/Vault acceptance

`tests/IntegrationTests/TenantSqlVaultIsolationAcceptanceTests.cs` provisions two synthetic tenants into unique databases on a disposable SQL Server, creates separate per-tenant SQL logins, writes each generated credential through a Vault writer AppRole, reads it back through the Vault reader AppRole, proves each login can read its own tenant sentinel, and proves each login is denied access to the other tenant database and Platform database. The latest acceptance also obtains signed access tokens from the production tenant-selection endpoint, validates them with the API JWT bearer middleware, routes requests through `TenantDatabaseRouting` and the Vault credential reader, and verifies that a modified signature is rejected. The signing key and principal are acceptance-only; this does not verify production key custody or live host configuration. Its opt-in Compose file has a unique project/network/volume, no published ports, and runs against the explicitly selected Docker context:

```powershell
$env:TENANT_ACCEPTANCE_SQL_PASSWORD = [Convert]::ToBase64String([Security.Cryptography.RandomNumberGenerator]::GetBytes(48)) + 'aA1!'
$env:TENANT_ACCEPTANCE_VAULT_ROOT_TOKEN = [Convert]::ToBase64String([Security.Cryptography.RandomNumberGenerator]::GetBytes(48))
$project = 'nexora-tenant-isolation-acceptance-<unique-suffix>'
$compose = 'deploy/docker/docker-compose.tenant-isolation-acceptance.yml'
try {
  docker --context nexora-remote compose -p $project -f $compose up --detach --build
  # Poll `compose ps -q tenant-isolation-test` with `docker inspect` until it exits.
  # Read only the acceptance runner output; Vault's development startup log prints its temporary root token.
  docker --context nexora-remote logs "$project-tenant-isolation-test-1"
} finally {
  docker --context nexora-remote compose -p $project -f $compose down --volumes --remove-orphans
  Remove-Item Env:TENANT_ACCEPTANCE_SQL_PASSWORD, Env:TENANT_ACCEPTANCE_VAULT_ROOT_TOKEN -ErrorAction SilentlyContinue
}
```

The fixture fails closed unless `AIERP_TENANT_ISOLATION_ACCEPTANCE_DISPOSABLE_INSTANCE` carries the explicit disposable-target confirmation. Never use the release stack's `.env`, SQL connection, Vault endpoint or credentials for this test. The 2026-10-26 runs passed two ERP and Studio tenant databases, API enqueue/idempotency replay, actual Worker claim/complete/activation, Vault write/read-back, own-database access and cross-database denial (1/1). A later run also seeded an expired `Running` lease to simulate worker loss and injected one transient Vault write failure; the actual worker reclaimed the expired job and completed it, and successfully retried the Vault write. Attempt counts reflected the overlap when both conditions affected the same job. The retry exposed and fixed a SQL principal SID/role membership query that attempted to convert the login name to `smallint`. Production-signed key custody, legacy restore/copy, production SQL grants, the still-configured global `aierp_data_runtime` template principal, and production Vault per-tenant policy remain separate rollout gates.

There is no HTTP health endpoint on this worker; Compose intentionally does not advertise a healthcheck. Its queue/SQL readiness must be covered by job-level telemetry and an acceptance probe, not an invented HTTP health URL.
