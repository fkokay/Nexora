# AI ERP Platform

Multi-tenant ERP platform foundation with a separately hosted AI Development Service. The current delivery includes authentication, tenant selection, a dashboard, AI Studio request intake, Cari, Stok & Depo, sales, and purchasing workflows.

See [master prompt phase status](docs/phase-status.md) for the verified implementation scope and remaining work by phase.

Use the [project map](docs/project-map.md) to find the right service, frontend, test suite, or deployment area when developing.

## Run locally

1. Copy `.env.example` to `deploy/docker/.env` and replace the sample values.
2. Start the local stack: `docker compose --env-file deploy/docker/.env -f deploy/docker/docker-compose.yml up --build -d`. This starts the ERP Web on port 5173 and Development Studio on port 5174 along with SQL Server and backend services.
3. For ERP Web hot reload, stop the Compose `erp-web` service and run `npm ci` then `npm run dev -- --port 5175` from `frontend/erp-web`; the API permits this development origin.
4. Open `http://localhost:5173` and use the bootstrap credentials configured in `deploy/docker/.env`.

### Local monitoring

Start the optional Prometheus collector with `docker compose --profile monitoring --env-file deploy/docker/.env -f deploy/docker/docker-compose.yml up -d prometheus`, then open `http://localhost:9090`. The UI is bound to loopback and is not exposed by the public-ingress profile. It retains at most 15 days or 2 GB of metrics. Alerts are evaluated locally; notification delivery is not configured.

The local compose profile bootstraps the first user and applies versioned EF Core migrations. The migration baseline adopts the original schema without dropping data. Cari records are tenant-scoped, unique by code within each tenant, searchable, and protected against concurrent overwrites with SQL Server rowversion. Current Cari features include tenant-owned groups and addresses, account currency, risk limit, payment term, append-only debit/credit movements, balance calculation, and linked reversal entries. Stok & Depo includes tenant-scoped stock cards and warehouses, per-warehouse physical, reserved, available, and valued balances with minimum-stock indicators, append-only receipt/issue movements and tenant-base-currency unit-cost snapshots, negative-stock prevention, and linked reversal entries. TenantAdmins can allocate landed costs to posted receipt lines by value, quantity, or equally and append reversible cost revaluations without changing stock quantity. Stock cards can define alternate units for manual receipts/issues; the original entry unit is retained while inventory is stored in the base unit. Lot/serial tracking is available for stock movements, receipts, deliveries, returns, and transfers. Alternate units are available across commercial workflows, including quotes, purchase requests, receipts, deliveries, returns, and transfers; quantities and prices are normalized to the stock card base unit. Depots can be deactivated only with zero balance and later reactivated. Multi-line warehouse transfers write paired issue/receipt movements atomically, use idempotency keys, and can be voided only as a whole when destination stock remains available. Stock cards can be edited with rowversion conflict checks and deactivated/reactivated; deactivation is blocked while warehouse stock or open order lines remain. TenantAdmins can define tenant-scoped stock-card custom fields (text, decimal, date, boolean); values are validated, and deactivated field values are retained. TenantAdmins can edit labels and text limits; each metadata change, deactivation, and restore is recorded as an immutable revision. Earlier metadata can be restored as a new revision. Field code and data type stay immutable; the last 50 value changes per stock-card field are available with old/new values and actor/time metadata; Tenant users can restore a prior value with explicit confirmation, which appends a new history entry. Required fields are enforced on both stock-card creation and value updates; existing cards must be populated before a field can be made required. Customer accounts also support tenant-scoped text, decimal, date, and boolean custom fields with type validation; required customer fields are enforced on card creation and value updates; existing cards must be populated before an optional field can be made required. Customer field definitions now keep immutable, tenant-scoped revisions (including a baseline for existing definitions); TenantAdmins can restore compatible metadata as a new revision. Customer-card field values keep the last 50 append-only changes with old/new values, definition version, actor, and timestamp; initial values are included in the migration baseline, and a prior value can be restored with confirmation as a new history event. TenantAdmins can review tenant-scoped audit events with date, action, and resource filters in the ERP İşlem Kayıtları view. TenantAdmins can also configure typed custom fields on purchase requests; required values are checked at submission, editable until review, and retained with append-only value and metadata histories. Sales supports quote draft, send, accept/reject, single-conversion sales orders, warehouse reservations for open order quantities, partial delivery notes, and transactional warehouse stock issue. Reservations are tied to an order line and warehouse, reduce available stock, are consumed at delivery, and can be released by a TenantAdmin with a reason. A posted delivery can create one invoice; posting records the customer debit, checks the risk limit, and invoice voids preserve the ledger with a linked credit reversal. Invoice detail supports partial or full collections with an invoice allocation; collection posting creates a customer credit entry and collection void adds a linked debit reversal while restoring the invoice balance. Invoice returns can be partial by invoiced line, receive stock into a selected warehouse, and record a customer credit; return void writes reverse stock and ledger movements, subject to available stock. Purchasing supports tenant-scoped internal stock requests with separate TenantAdmin approval/rejection (request owners cannot decide their own requests). TenantAdmins can record supplier offers against approved requests, snapshot per-line price/discount/tax and validity, compare totals in the tenant base currency using manually maintained, tenant-scoped exchange rates dated on or before each offer; missing rates remain explicitly unconverted, and convert one valid offer into a linked order; competing offers are marked not selected. Direct conversion remains available when quotes were not collected. Supplier orders support partial/full goods receipts and receipt-linked purchase invoices. Invoice totals snapshot received order pricing, due date follows supplier payment terms, and posting increases the supplier's credit balance. Partial supplier payments are capped at the outstanding invoice amount and reduce the supplier balance. Invoice/payment voids preserve the ledger with linked reversals; receipt void requires the invoice and its payments to be voided first. The AI Development Service remains a separate host. It now includes a tenant-scoped project registry with explicit Viewer, Contributor, and Maintainer access grants. Development requests can be linked to a project and are filtered by project membership; Viewer is read-only. Contributor/Maintainer users can request a branch-specific workspace, with approval/rejection by a tenant administrator or project Maintainer. After approval, a tenant administrator or project Maintainer can create an isolated shallow checkout through the separate Workspace Runner. The runner uses a short-lived service token scoped to one workspace and one operation, has no database or Docker socket, stores checkouts in its own volume, and fetches only from the configured public HTTPS Git host allowlist (GitHub by default). It records the commit SHA and Project Explorer lists file names, kinds, and sizes, with audited read-only previews for UTF-8 text files up to 128 KiB. It also produces an audited, bounded project map from file names and extensions, skipping Git metadata and generated/dependency directories without reading source contents. It hides `.git`, rejects traversal, refuses binary and oversized files, and does not execute repository code; test execution uses the separate sandbox described below. Git credentials are not accepted or stored. AI Architect can produce a schema-validated plan from an explicitly confirmed user request and bounded project metadata; source files are not sent. Contributors and tenant administrators can explicitly save plans to tenant/project/workspace history with branch and commit metadata; the original request text is not stored, and saving does not apply the plan. AI Developer can propose a replacement for one selected, allowlisted source file (up to 32 KiB) or create one new source file; new-file requests share only the path and request, while selected file content requires separate sharing consent. A second explicit approval can apply it to the existing file or create one new source file in an existing directory in the isolated checkout; updates use an SHA-256 stale-source check and creation refuses to overwrite a target. Exact pre-apply bytes are stored outside Git; an audited history and line diff are available, and a separate approval restores the preceding bytes only if the file still matches the applied hash (up to 200 history entries per workspace). Newly created files are marked in history and rollback deletes them only if their applied hash still matches. Source sharing, approval, application, diff access, and restore are audited. AI suggestions are not executed when applied. Maintainers and TenantAdmins can separately run discovered .NET tests, Python pytest suites, dependency-free Node.js built-in tests, standard-library-only Go test packages, and standalone dependency-free Rust Cargo packages in the networkless sandbox after explicit confirmation. Go modules declaring `require`, `replace`, or `toolchain` directives and Rust manifests declaring crate dependencies or Cargo workspaces are reported unavailable; Go/Rust crate dependencies, Node.js dependencies, and project-specific Python packages are not installed, and npm scripts are never invoked. AI Developer also supports coordinated proposals for 2–5 selected source files (up to 64 KiB total); each file is reviewed and applied separately with the existing stale-source and approval checks. Configure OPENAI_API_KEY to enable the Responses API provider (unset means disabled).
The `OPENAI_API_KEY` entry in `.env.example` is optional. Set it in `deploy/docker/.env` to enable AI features; the key is passed only to the AI Service container and is never stored in the browser.

TenantAdmins can manage the Development Studio chat provider and OpenAI/NVIDIA NIM API keys from **Ayarlar → AI sağlayıcı ayarları**. Keys are encrypted in the platform database and never returned to the browser; configure a random base64 256-bit `AI_SETTINGS_ENCRYPTION_KEY` in `deploy/docker/.env` before saving a key. The provider setting currently controls Studio chat; other structured AI workflows continue to use the server's OpenAI configuration.

For private GitHub checkout, configure the GitHub App once with `GITHUB_APP_ID`, `GITHUB_APP_SLUG`, and `GITHUB_APP_PRIVATE_KEY_PEM` in `deploy/docker/.env`; set the App Setup URL to `http://localhost:5081/studio/github/setup-callback` for local Compose. A project Maintainer or TenantAdmin then uses **GitHub ile yetkilendir** in Studio; each installation ID is stored against its project, so adding another repository does not require editing `.env`. Checkout uses a short-lived token restricted to that repository with Contents read permission; the token is passed only over the internal AI Service/Runner connection and is not saved. PR publishing uses a separate token with write permissions and still requires explicit approval.

Finance includes tenant-scoped exchange rates, open-invoice exposure and maturity reporting, balanced period-end FX revaluation vouchers, plus a configurable tenant chart of accounts and account mappings. TenantAdmins can transfer posted sales and purchase invoices, sales deliveries and returns, supplier returns, customer collections and supplier payments, including cash/bank-linked, card, and check methods, FX revaluation vouchers, and inventory cost-adjustment sources into immutable balanced general-ledger entries. Cash/bank transfers use account-specific mappings; card and check activity uses configurable clearing/portfolio accounts. Sales invoice transfers use receivable, revenue, and (when needed) calculated-tax mappings; purchase invoice transfers use payable, cost, and (when needed) recoverable-tax mappings, converting foreign-currency amounts with the latest rate on or before the source date.  TenantAdmins can also create balanced manual journal entries and reverse any manual or transferred source entry once using an immutable counter-entry with a reason; transferred source records must be reversed before they can be voided. A date-filtered trial balance and CSV export are available. Sales and purchasing invoices can be transferred by a TenantAdmin; collections and payments can be transferred manually using cash/bank accounts or configured card/check clearing mappings; sales delivery transfers debit sold-goods cost and credit inventory using the posted stock cost snapshot. Purchase receipts debit inventory and credit a configured goods-received-not-invoiced account; the following purchase invoice clears that accrual and records any net-cost variance. Return transfers also post the related inventory and cost-of-goods adjustment using the stock movement cost snapshot.

Supplier returns can be partial by invoice line and reduce both warehouse stock and supplier payable; voiding them appends opposite stock and ledger entries. Posted supplier returns are included in the invoice open balance, and invoice/receipt voids respect linked payments and returns.

See [docs/architecture.md](docs/architecture.md) for the architecture boundary, tenant security model, and current limitations.

Tenant administrators can review and export a bounded, aggregate HR period summary for employees, attendance, and leave. See [docs/human-resources-operations.md](docs/human-resources-operations.md) for access, period semantics, audit events, and scope.


The AI Development Studio has its own Vite frontend at `frontend/development-studio` and a separate Compose-served Nginx host on port 5174. The ERP login can open this client in a new tab; sign-in is performed against the same Platform API.

### Local release staging

Release packages can be deployed to a project-scoped Docker Compose staging stack from Development Studio after independent candidate approval. The staging UI is bound to `localhost` only; each stack has its own SQL Server and persistent workspace volumes. Redeploy replaces the app code while retaining staging data. Rollback deploys a previously successful package against that same database and does not roll back database migrations. Destroying staging removes its services and persistent volumes after a separate confirmation.

The internal Release Deployer is the only service with Docker Engine socket access. Docker socket access grants host-wide container control, so run this integration only on a trusted machine. The Studio also supports local Docker Compose production promotion: a different TenantAdmin must approve the staging promotion, then an administrator separately confirms deployment and schema migration. Production runs in a project-scoped stack with a persistent SQL Server data volume and a separate persistent `aierp-production-backups` Docker volume, both on this host, and a localhost-only port. Before an update, SQL Server writes a checksum-verified backup into the backup volume; the Deployer verifies it can read the resulting file before proceeding. After a failed release, the Deployer attempts to restart the previous application stack and health-checks it when Compose starts successfully. The health-check result is written only to Deployer logs. A TenantAdmin can restore the prior application/database pair from Production history after a separate confirmation that warns later ERP records will be replaced; the Deployer first verifies the selected backup and makes a verified safety backup of the current database. Production and the primary API/Studio ports remain loopback-bound on the host. SQL and backup volumes are local to this host; the Release Deployer now refreshes the active Production restore point daily at 02:00 UTC.

Production SQL databases are backed up daily at 02:00 UTC by the Release Deployer. The API and AI Service briefly stop while each active project's database set is captured. Each set gets an SQL database-name manifest, SQL Server backup checksums, and `RESTORE VERIFYONLY` validation. The scheduled snapshot is staged and then replaces the active release's current restore point, so it is available from that release in Studio Production history. In shared-database mode, `AIERPPlatform` contains ERP and Studio data. With database separation enabled, the set includes `AIERPPlatform`, `AIERPStudio`, and every provisioned `AIERPTenant_<tenant-guid>` database. This covers SQL data only. Persistent workspace checkouts, queued/running test snapshots, release packages, staging/production Deployer state and generated deployment configuration, and Caddy data/config have a separate writer-quiesced volume snapshot.


Create a snapshot of the persistent non-SQL volumes on Windows with `powershell -ExecutionPolicy Bypass -File deploy/docker/Backup-PersistentVolumes.ps1`. The script stops only currently running writers, creates a timestamped archive and SHA-256 sidecar in `aierp-production-backups`, then restarts the same services. Local snapshots retain 30 days by default (`VOLUME_BACKUP_RETENTION_DAYS` can be set from 1 to 3650). The optional offsite sidecar copies completed snapshots and excludes temporary `.partial` files. These archives include user source, Deployer state and generated environment files, release packages, queued test snapshots, and certificates; they may contain credentials. Protect the local backup volume and keep `.env`/encryption keys in a separate secret manager.

To restore a volume archive, first copy the archive and its `.sha256` file into `aierp-production-backups` if restoring from offsite. Run `powershell -ExecutionPolicy Bypass -File deploy/docker/Backup-PersistentVolumes.ps1 -RestoreFrom nexora-volumes-<UTC timestamp>-<id>.tar.gz` and type the requested confirmation. The script makes a safety snapshot before replacing the non-SQL volumes and attempts to restore that safety snapshot if the requested restore fails. SQL data is deliberately excluded; restore databases through Production history or the documented database restore procedure. Test volume restore regularly on a disposable Compose project before relying on it for disaster recovery.
Optional encrypted offsite copying is available with `docker compose --profile offsite-backup --env-file deploy/docker/.env -f deploy/docker/docker-compose.yml up -d offsite-backup`. In the private `.env`, set the provider's HTTPS endpoint, bucket, access key, secret key, prefix, and rclone-obscured crypt password. Generate and store the password with your approved secret manager; rclone's obscured form is reversible, so protect it as a secret. The sidecar encrypts backup contents and names, copies them without pruning, then runs `rclone check --download` to compare remote content. A failed copy or verification exits the container and Compose restarts it. Set bucket versioning and lifecycle retention at the provider: remote objects are intentionally never deleted by this stack. Check `docker compose ... logs -f offsite-backup` and stop with `docker compose ... --profile offsite-backup stop offsite-backup`.

On Windows, run the value-free configuration check before starting the sidecar: `.\deploy\docker\validate-offsite-backup.ps1 -ProbeRemote`. It checks required fields and Compose syntax, then performs a read-only remote listing to validate the S3 credentials and crypt configuration; it suppresses values and remote names. The sample endpoint/bucket in `.env.example` deliberately fails this check. After the probe passes, start the sidecar with the command above and confirm the logs show both copy and download-check success.

To restore an offsite SQL snapshot, find its project and deployment GUIDs in the Production history, then copy that encrypted set back into the shared backup volume (the glob copies the `.bak` files and manifest for that set):

```sh
docker compose --profile offsite-backup --env-file deploy/docker/.env -f deploy/docker/docker-compose.yml run --rm --no-deps offsite-restore copy crypt: /production-backups --config /dev/null --include '*-<project-guid-without-hyphens>-<deployment-guid-without-hyphens>.*'
```

Then use Studio **Production history → Restore** for that deployment and complete its typed confirmation.
For a non-SQL volume archive, copy the encrypted object from the configured crypt remote and keep the checksum sidecar beside it:

```sh
docker compose --profile offsite-backup --env-file deploy/docker/.env -f deploy/docker/docker-compose.yml run --rm --no-deps offsite-restore copy "crypt:nexora-volumes-<UTC timestamp>-<id>.tar.gz" /production-backups --config /dev/null
docker compose --profile offsite-backup --env-file deploy/docker/.env -f deploy/docker/docker-compose.yml run --rm --no-deps offsite-restore copy "crypt:nexora-volumes-<UTC timestamp>-<id>.tar.gz.sha256" /production-backups --config /dev/null
```

Then run the volume restore command above. The local checksum is verified before replacement; use the encrypted offsite copy and provider-side versioning for protection against local archive replacement. The Deployer verifies the database set, takes a verified safety snapshot of current data, stops writers, restores the selected databases with checksums, starts the matching application package, and health-checks it. Exercise this recovery path periodically. Never restore `.bak` files directly over SQL data files or delete the safety snapshot before the application is verified.

Optional public HTTPS access to the shared Development Studio is available with `docker compose --profile public-ingress --env-file deploy/docker/.env -f deploy/docker/docker-compose.yml up -d public-ingress`. Set `PUBLIC_DOMAIN` to a DNS name pointing to this host, `PUBLIC_INGRESS_ORIGIN` to its `https://` origin, and open inbound TCP 80/443 (UDP 443 is optional for HTTP/3). Caddy obtains and renews certificates automatically. Set `GITHUB_APP_SETUP_CALLBACK_URL` and `GITHUB_STUDIO_REDIRECT_URL` to the matching public HTTPS URLs when using the GitHub App. This profile fronts Development Studio only; it does not publish generated Production stacks or the loopback-only ERP Web. The current deployment supports persistent single-host services, local container restart, verified database restore, and optional encrypted offsite backup. It does not provide automatic host/database failover, multi-host traffic routing, or coordinated multi-instance deployment. Readiness probes now check the platform and Studio databases. Review the [HA decision checklist and support boundary](docs/architecture.md#availability-deployment-and-recovery-boundary) before selecting a production topology. The first production bootstrap credentials are shown once to the administrator who starts the deployment. No production stack is started until an approved package is explicitly deployed from Studio.
