# AI ERP Platform

Multi-tenant ERP platform foundation with a separately hosted AI Development Service. The current delivery includes authentication, tenant selection, a dashboard, AI Studio request intake, Cari, Stok & Depo, sales, and purchasing workflows.

## Run locally

1. Copy `.env.example` to `deploy/docker/.env` and replace the sample values.
2. Start SQL Server and both backend hosts: `docker compose --env-file deploy/docker/.env -f deploy/docker/docker-compose.yml up --build -d`.
3. Run the web UI from `frontend/erp-web`: `npm install` then `npm run dev`.
4. Open `http://localhost:5173` and use the bootstrap credentials configured in `deploy/docker/.env`.

The local compose profile bootstraps the first user and applies versioned EF Core migrations. The migration baseline adopts the original schema without dropping data. Cari records are tenant-scoped, unique by code within each tenant, searchable, and protected against concurrent overwrites with SQL Server rowversion. Current Cari features include tenant-owned groups and addresses, account currency, risk limit, payment term, append-only debit/credit movements, balance calculation, and linked reversal entries. Stok & Depo includes tenant-scoped stock cards and warehouses, per-warehouse physical, reserved, available, and valued balances with minimum-stock indicators, append-only receipt/issue movements and tenant-base-currency unit-cost snapshots, negative-stock prevention, and linked reversal entries. Depots can be deactivated only with zero balance and later reactivated. Multi-line warehouse transfers write paired issue/receipt movements atomically, use idempotency keys, and can be voided only as a whole when destination stock remains available. Stock cards can be edited with rowversion conflict checks and deactivated/reactivated; deactivation is blocked while warehouse stock or open order lines remain. TenantAdmins can define tenant-scoped stock-card custom fields (text, decimal, date, boolean); values are validated, and deactivated field values are retained. TenantAdmins can edit labels and text limits; each metadata change, deactivation, and restore is recorded as an immutable revision. Earlier metadata can be restored as a new revision. Field code and data type stay immutable; the last 50 value changes per stock-card field are available with old/new values and actor/time metadata; Tenant users can restore a prior value with explicit confirmation, which appends a new history entry. Required fields are enforced on both stock-card creation and value updates; existing cards must be populated before a field can be made required. Customer accounts also support tenant-scoped text, decimal, date, and boolean custom fields with type validation; required customer fields are enforced on card creation and value updates; existing cards must be populated before an optional field can be made required. Customer field definitions now keep immutable, tenant-scoped revisions (including a baseline for existing definitions); TenantAdmins can restore compatible metadata as a new revision. Customer-card field values keep the last 50 append-only changes with old/new values, definition version, actor, and timestamp; initial values are included in the migration baseline, and a prior value can be restored with confirmation as a new history event. TenantAdmins can review tenant-scoped audit events with date, action, and resource filters in the ERP İşlem Kayıtları view. TenantAdmins can also configure typed custom fields on purchase requests; required values are checked at submission, editable until review, and retained with append-only value and metadata histories. Sales supports quote draft, send, accept/reject, single-conversion sales orders, warehouse reservations for open order quantities, partial delivery notes, and transactional warehouse stock issue. Reservations are tied to an order line and warehouse, reduce available stock, are consumed at delivery, and can be released by a TenantAdmin with a reason. A posted delivery can create one invoice; posting records the customer debit, checks the risk limit, and invoice voids preserve the ledger with a linked credit reversal. Invoice detail supports partial or full collections with an invoice allocation; collection posting creates a customer credit entry and collection void adds a linked debit reversal while restoring the invoice balance. Invoice returns can be partial by invoiced line, receive stock into a selected warehouse, and record a customer credit; return void writes reverse stock and ledger movements, subject to available stock. Purchasing supports tenant-scoped internal stock requests with separate TenantAdmin approval/rejection (request owners cannot decide their own requests). TenantAdmins can record supplier offers against approved requests, snapshot per-line price/discount/tax and validity, compare totals in the tenant base currency using manually maintained, tenant-scoped exchange rates dated on or before each offer; missing rates remain explicitly unconverted, and convert one valid offer into a linked order; competing offers are marked not selected. Direct conversion remains available when quotes were not collected. Supplier orders support partial/full goods receipts and receipt-linked purchase invoices. Invoice totals snapshot received order pricing, due date follows supplier payment terms, and posting increases the supplier's credit balance. Partial supplier payments are capped at the outstanding invoice amount and reduce the supplier balance. Invoice/payment voids preserve the ledger with linked reversals; receipt void requires the invoice and its payments to be voided first. The AI Development Service remains a separate host. It now includes a tenant-scoped project registry with explicit Viewer, Contributor, and Maintainer access grants. Development requests can be linked to a project and are filtered by project membership; Viewer is read-only. Contributor/Maintainer users can request a branch-specific workspace, with approval/rejection by a tenant administrator or project Maintainer. After approval, a tenant administrator or project Maintainer can create an isolated shallow checkout through the separate Workspace Runner. The runner uses a short-lived service token scoped to one workspace and one operation, has no database or Docker socket, stores checkouts in its own volume, and fetches only from the configured public HTTPS Git host allowlist (GitHub by default). It records the commit SHA and Project Explorer lists file names, kinds, and sizes, with audited read-only previews for UTF-8 text files up to 128 KiB. It also produces an audited, bounded project map from file names and extensions, skipping Git metadata and generated/dependency directories without reading source contents. It hides `.git`, rejects traversal, refuses binary and oversized files, and does not execute repository code; test execution uses the separate sandbox described below. Git credentials are not accepted or stored. AI Architect can produce a schema-validated plan from an explicitly confirmed user request and bounded project metadata; source files are not sent. Contributors and tenant administrators can explicitly save plans to tenant/project/workspace history with branch and commit metadata; the original request text is not stored, and saving does not apply the plan. AI Developer can propose a replacement for one selected, allowlisted source file (up to 32 KiB) or create one new source file; new-file requests share only the path and request, while selected file content requires separate sharing consent. A second explicit approval can apply it to the existing file or create one new source file in an existing directory in the isolated checkout; updates use an SHA-256 stale-source check and creation refuses to overwrite a target. Exact pre-apply bytes are stored outside Git; an audited history and line diff are available, and a separate approval restores the preceding bytes only if the file still matches the applied hash (up to 200 history entries per workspace). Newly created files are marked in history and rollback deletes them only if their applied hash still matches. Source sharing, approval, application, diff access, and restore are audited. AI suggestions are not executed when applied. Maintainers and TenantAdmins can separately run discovered .NET tests, Python pytest suites, dependency-free Node.js built-in tests, standard-library-only Go test packages, and standalone dependency-free Rust Cargo packages in the networkless sandbox after explicit confirmation. Go modules declaring `require`, `replace`, or `toolchain` directives and Rust manifests declaring crate dependencies or Cargo workspaces are reported unavailable; Go/Rust crate dependencies, Node.js dependencies, and project-specific Python packages are not installed, and npm scripts are never invoked. AI Developer also supports coordinated proposals for 2–5 selected source files (up to 64 KiB total); each file is reviewed and applied separately with the existing stale-source and approval checks. Configure OPENAI_API_KEY to enable the Responses API provider (unset means disabled).
The `OPENAI_API_KEY` entry in `.env.example` is optional. Set it in `deploy/docker/.env` to enable AI features; the key is passed only to the AI Service container and is never stored in the browser.

For private GitHub checkout, configure `GITHUB_APP_ID`, `GITHUB_APP_INSTALLATION_ID`, and `GITHUB_APP_PRIVATE_KEY_PEM` in `deploy/docker/.env`, install that GitHub App on the repository, then recreate the Compose services. Checkout uses a short-lived token restricted to that repository with Contents read permission; the token is passed only over the internal AI Service/Runner connection and is not saved. Missing or denied authorization is shown in Studio as a GitHub authorization message. PR publishing uses a separate token with write permissions and still requires explicit approval.

Supplier returns can be partial by invoice line and reduce both warehouse stock and supplier payable; voiding them appends opposite stock and ledger entries. Posted supplier returns are included in the invoice open balance, and invoice/receipt voids respect linked payments and returns.

See [docs/architecture.md](docs/architecture.md) for the architecture boundary, tenant security model, and current limitations.


The AI Development Studio has its own Vite frontend at `frontend/development-studio` and a separate Compose-served Nginx host on port 5174. The ERP login can open this client in a new tab; sign-in is performed against the same Platform API.

### Local release staging

Release packages can be deployed to a project-scoped Docker Compose staging stack from Development Studio after independent candidate approval. The staging UI is bound to `localhost` only; each stack has its own SQL Server and persistent workspace volumes. Redeploy replaces the app code while retaining staging data. Rollback deploys a previously successful package against that same database and does not roll back database migrations. Destroying staging removes its services and persistent volumes after a separate confirmation.

The internal Release Deployer is the only service with Docker Engine socket access. Docker socket access grants host-wide container control, so run this integration only on a trusted machine. The Studio also supports local Docker Compose production promotion: a different TenantAdmin must approve the staging promotion, then an administrator separately confirms deployment and schema migration. Production runs in a project-scoped stack with a persistent SQL Server data volume and a separate persistent `aierp-production-backups` Docker volume, both on this host, and a localhost-only port. Before an update, SQL Server writes a checksum-verified backup into the backup volume; the Deployer verifies it can read the resulting file before proceeding. After a failed release, the Deployer attempts to restart the previous application stack and health-checks it when Compose starts successfully. The health-check result is written only to Deployer logs. A TenantAdmin can restore the prior application/database pair from Production history after a separate confirmation that warns later ERP records will be replaced; the Deployer first verifies the selected backup and makes a verified safety backup of the current database. This is a single-host setup and does not provide off-host backups, high availability, or public ingress. The first production bootstrap credentials are shown once to the administrator who starts the deployment. No production stack is started until an approved package is explicitly deployed from Studio.
